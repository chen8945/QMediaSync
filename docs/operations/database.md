## 引擎与初始化

QMediaSync 支持 SQLite 和 PostgreSQL，默认使用 PostgreSQL。程序和 Docker 镜像均不提供 PostgreSQL 服务进程。数据库配置通过 `config/config.yaml` 保存；首次配置、端口和 PostgreSQL 要求见 [配置、密钥与日志](configuration.md)。

SQLite 连接使用 WAL 日志模式、`synchronous = NORMAL` 和 10 秒 `busy_timeout`，并且连接池固定为一个连接（`MaxOpenConns` 和 `MaxIdleConns` 均为 1，连接不设置存活和空闲上限）。SQLite 同一时间只允许一个写事务：多连接时，事务读取快照之后如果其他连接提交了写入，本事务的写升级会立即失败并返回 `SQLITE_BUSY`（快照冲突），`busy_timeout` 不会重试这种错误。单连接把所有语句串行化到进程内的连接锁上排队，写入不再返回 `database is locked`。`MaxOpenConns` 不适用于 SQLite 引擎，只作用于 PostgreSQL。

因此 SQLite 下的写事务体内不得再通过全局 `db.Db` 发起新语句，必须使用事务自身的 `tx`：单连接会让这种嵌套语句等待自己持有的连接而死锁。PostgreSQL 连接池仍按 `config/config.yaml` 的 `maxOpenConns` 和 `maxIdleConns` 配置。

SQLite 和 PostgreSQL 共用 GORM 日志配置：忽略 `ErrRecordNotFound` 日志，保留真实 SQL 错误和超过 200 毫秒的慢查询。忽略日志不改变查询返回值；空库初始化和后台队列无待办时仍由业务代码处理“记录不存在”，不会因此持续刷出错误日志。

首次启动时，只有注册的业务表和 `migrator` 表都不存在，程序才在一个事务中创建所有表和必要索引、初始化默认设置／刮削设置及分类／Emby 配置，最后写入当前版本。任一步失败都会回滚本次初始化并停止启动；根据错误日志排除故障后，重新启动即可重试。首次空库直接初始化到当前结构版本，不逐个回放历史迁移；首个管理员通过启动日志中的初始化码创建。已有业务表却缺少版本表，或版本记录缺失、重复、超出支持范围时，拒绝启动和修复，不能猜测当前版本。

这一回滚保证适用于当前程序执行的首次初始化。旧程序已经留下版本表但缺少其他结构或数据的数据库，不会自动被当作空库重新初始化；应先保留备份、核查日志和实际缺失，再按修复与恢复流程处理。

已有数据库启动时，`Migrate()` 按 `migrator.version_code` 顺序执行补丁并逐步推进版本。新增或修改表、字段和迁移时必须同时更新 [数据库 schema 与迁移](../reference/database-schema.md)。

数据库及后台队列初始化后，启动流程同步恢复 Emby Webhook 工作并启动 worker，成功后才进入 HTTP 服务和 Windows 托盘。恢复或 worker 启动失败时记录原因，停止已启动的队列并释放应用资源，由主流程以非零状态退出；排除故障后重新启动，避免留下只有托盘、没有服务的进程。

本地管理员恢复使用独立的已有数据库连接：SQLite 以 `mode=rw` 打开已有普通文件，PostgreSQL 只连接指定数据库；两者均不建库、不迁移、不启动后台保活，连接池限制为一个连接。认证变更以单个事务提交，失败回滚。它与备份恢复、数据库修复是不同操作，具体契约见 [本地管理员恢复](../architecture/authentication-sessions.md#本地管理员恢复)，使用方法见 [部署说明](deployment.md#管理员恢复)。

## 旧内嵌数据库

当前版本不再启动内嵌 PostgreSQL，也不提供旧库迁移网页、迁移导出或 `backups/migrate.zip` 自动导入。普通备份恢复和数据库 schema 升级仍按本文及 schema 文档执行。

如需从内置 PostgreSQL 迁移，可先使用原作者的 `v0.14.23` 或本项目的 `v0.15.17` 版本。两个过渡版本的迁移目标均为外部 PostgreSQL，不能在旧迁移向导中直接选择 SQLite。先保留停机后的整个配置目录、数据库数据目录、原镜像或程序版本，再由过渡版本导出迁移包、保存外部 PostgreSQL 配置，并由同一过渡版本重启完成自动导入；迁移包须另行保存副本，旧导入流程结束会删除工作副本。

旧流程部分导出或导入错误只记日志后继续，页面显示完成或 `migrate.zip` 消失都不能代替数据核对。检查日志、账号、同步目录、任务记录等内容，并验证登录及凭据；旧 JSON 导出还可能遗漏 API Key 哈希和两步验证密钥，需要准备重新创建 API Key、重新设置两步验证。行为依据见 [本项目过渡版迁移服务](https://github.com/chen8945/QMediaSync/blob/8c6edf8af4a846cf210a12c6ef4e6d5522251add/backend/internal/migrate/server.go)和[恢复实现](https://github.com/chen8945/QMediaSync/blob/8c6edf8af4a846cf210a12c6ef4e6d5522251add/backend/internal/backup/restore.go)。

核对外部 PostgreSQL 数据完整后，再用当前版本连接该数据库并执行正常 schema 升级。需要改用 SQLite 时，先在当前版本重新备份，再按本文的跨引擎恢复流程迁入 SQLite；不能把旧过渡版的迁移 ZIP 当作当前格式的备份直接上传。当前版本遇到以下状态会拒绝继续：

- PostgreSQL 配置显式指定 `postgresType: embedded`，或使用未知引擎、未知 PostgreSQL 模式。
- 配置目录下存在 `backups/migrate.zip`：正常启动和管理员恢复均拒绝操作，不导入或删除该文件。
- 主配置缺失但存在 `config/postgres`：拒绝进入首次配置向导，避免把旧实例当作空实例重新初始化。

旧 SQLite 配置中未使用的 `postgresType: embedded` 不影响 SQLite 连接。已经切换到受支持数据库的实例可以保留旧数据目录；程序不会自动删除 `config/postgres`、`config/postgres-backup` 或旧 PostgreSQL 二进制目录。确认数据完整后，由维护者自行归档或清理，不能靠删除未完成迁移包来代替数据核对。

## 修复与清库

`POST /api/database/repair` 和每日修复先验证数据库版本记录，再对 `AllTables` 执行结构补齐，建立同步文件查询、STRM 队列排序和活跃上传／下载去重索引，从原收件、状态和证据重建 Emby 派生索引，并修复 PostgreSQL 主键序列。序列调整在持有表锁的事务中进行，保留已分配序列值的高水位，避免并发插入使序列倒退。

修复用于补齐结构、派生索引和序列，不恢复丢失记录，也不修复数据库文件的物理损坏。现有去重修复会补齐定位摘要，并取消冲突的重复活跃传输任务；它不删除业务记录，但会改变这些任务的状态。缺失或不可信的版本信息需要根据备份和实际结构核查，修复不会伪造版本或重新播种默认数据。

前端只有在 HTTP 与业务响应都成功时才提示修复成功；失败使用安全错误说明，不展示数据库内部异常。

`POST /api/database/delete-all-table` 调用 `BatchDropTable()` 删除 `AllTables` 中的全部表，属于高风险清库操作。执行前必须确认备份可用，并在维护窗口内操作。

## 备份

备份配置存储在数据库的 `backup_config`，不在 `config/config.yaml`。默认自动备份关闭；默认 Cron 是 `0 3 * * *`，默认保留 7 天、最多保留 10 份。服务启动时会按“已启用且 Cron 非空”创建定时任务；配置保存成功后统一重建 Cron，禁用会立即移除旧计划，无需重启。已开始执行的备份不会因关闭开关而中断。手动备份和定时备份不会并行执行。

备份文件始终写入配置目录下的 `backups/`，命名为 `backup_<类型>_<时间>.zip`。新建手动与定时备份的类型分别使用 `manual`、`auto`；历史 `定时` 类型记录和文件不改写，前端仍按自动备份展示。手动和自动备份使用同一实现：格式版本 2 将 `manifest.json` 放在 ZIP 根目录，表数据放在 `tables/<模型名>.json`，后缀为 `.json`，内容为每行一条记录的 JSON Lines。普通文件使用 ZIP Deflate 压缩。当前 `backup_path` 和 `backup_compress` 虽可保存到配置记录，但输出路径仍是 `backups/`，格式始终为 ZIP。

逻辑备份按 `AllTables` 的 GORM 持久化列导出，包含 API 隐藏的 `json:"-"` 字段，排除不入库的 `gorm:"-"` 字段。API Key 哈希、两步验证加密密钥、账号凭据、业务 JSON 和上传续传记录均参与备份。浏览器 `user_sessions` 明确排除；Emby 观察范围和历史成员索引属于可重建派生数据，也在清单中明确排除。新增表加入 `AllTables`、新增字段完成 schema 迁移后自动纳入，无需维护第二份备份字段清单；不支持的持久化类型会报错。备份进度从启动时就按排除后的实际导出表数统计。

历史升级可能留下已停用的列，清单明确声明以下排除规则：`emby_media_items.emby_data`、`backup_config.maintenance_mode`／`maintenance_mode_time`、`settings.bai_du_pan_qps`／`bai_du_pan_qpm`／`bai_du_pan_qph`／`bai_du_pan_qpt`、`sync_paths.baidu_sync_method`。备份不会修改或删除源库这些旧列；其他未注册的额外列仍报错，要求核查归属，不能自动当作无用数据丢弃。

每次新备份完成 ZIP 发布并成功保存完成记录后，程序才清理状态为 `completed` 的历史记录；生成或保存失败不清理旧包。保留天数和最大数量独立生效，任一条件命中都会删除文件及其记录；相同创建时间按记录 ID 从新到旧保留。清理失败记录日志，不改写已经完成的备份结果。应定期把完成的 ZIP 包复制到配置目录之外的独立存储，避免把唯一备份与运行数据放在同一磁盘。

下载任务备份包含执行地址、本地源路径和内容校验记录。备份文件包含敏感数据库数据，应与账号配置和凭据采用相同的保管方式。在支持 Unix 权限的平台，备份和上传临时目录设为 `0700`，表文件、清单和 ZIP 设为 `0600`；已存在的受管目录也会收紧权限，拒绝受管路径上的符号链接。新建 ZIP 先写入同目录临时文件，完整关闭并同步文件后，使用不覆盖目标的原子发布；支持的平台同步目录变更。进程在发布前中断只留下临时文件，不会暴露最终命名的半成品。启动时在实例锁内、后台任务和 HTTP 服务启动前，清理本功能明确命名的导出、发布、恢复和上传临时文件；不跟随符号链接，不清空备份目录，也不猜测旧数字目录的归属。

备份在一个一致读事务中读取全部表，不暂停后台队列和 Cron。PostgreSQL 使用可重复读快照；SQLite 文件数据库使用独立、短生命周期的只读连接，在 WAL 下读取快照，业务连接池仍保持单连接，导出不占用业务池的唯一连接。备份连接参与同一维护门禁，结束后关闭；长读快照可能延迟 WAL 回收，仍应为大库备份预留磁盘空间。清单记录格式／schema 版本、来源应用版本、表和列、明确排除项、行数和校验和。应用版本仅用于追溯；旧清单缺少该字段或来源应用版本不同，不影响按格式和 schema 规则恢复，字段契约见[逻辑备份的数据契约](../reference/database-schema.md#逻辑备份的数据契约)。该快照只覆盖数据库，不包含网盘、媒体文件或配置文件的同一时刻状态。

迁移时必须另行保留整个 `config/`，尤其是原 `encryption.key`，并在启动目标实例前放到位。数据库 ZIP 不打包配置，也不进行密钥迁移或重新加密。恢复预检会用当前进程已加载的密钥验证生效和待确认的非空 TOTP 密文；新包和无清单旧包均适用。无法解密时在修改数据库前拒绝，不记录明文或密文，不生成密钥，也不自动重新加密；没有相关密文的包不要求源实例密钥。保留原加密密钥后，原验证器可以继续使用；进程已经启动时只替换密钥文件不会刷新内存中的密钥，必须重启。

前端备份请求失败时保留配置和输入，不进入成功后的进度流程；写入已成功但列表刷新失败时单独提示加载问题。下载接口的 JSON 错误即使以 HTTP `200` 返回，也不能作为备份文件保存。错误反馈约定见 [前端开发约定](../engineering/frontend-development.md#api-响应与请求错误)。

## 备份和恢复状态

`GET /api/backup/status` 的 HTTP `200`、业务 `code=200` 表示成功读取任务快照，不代表备份或恢复成功。`data.status` 明确区分 `idle`（尚无任务）、`running`、`completed` 和 `failed`，原有 `is_running`、`count`、`total`、`error_msg` 等字段保留。启动接口在接受请求前占用运行状态并清除上一轮快照，避免并发启动或将上一轮终态当作新任务结果；状态读取返回独立快照。

任务快照的 `error_code` 只表达已知失败类别，`error_msg` 使用安全说明，不包含 SQL、内部路径或凭据；查询本身仍可返回 HTTP `200`。

| `error_code` | 含义 |
| --- | --- |
| `BACKUP_ARCHIVE_INVALID` | 归档损坏、内容缺失或不符合文件／数据契约 |
| `BACKUP_ARCHIVE_UNSUPPORTED` | 归档格式、压缩方式或数据库版本不兼容 |
| `BACKUP_ARCHIVE_LIMIT` | 文件大小、展开体积、记录或归档元数据超过支持范围 |
| `RESTORE_KEY_MISMATCH` | 当前已加载密钥无法解密备份中的两步验证数据 |
| `BACKUP_FAILED` / `RESTORE_FAILED` | 其余备份／恢复失败，不把未知 I/O 或数据库故障猜测为坏包 |

恢复终态另有 `restore_outcome`，与任务成功／失败及重启要求分别解释：

| 值 | 数据库结果 |
| --- | --- |
| `not_started` | 尚未执行数据库恢复修改 |
| `rolled_back` | 已确认本轮恢复事务回滚成功 |
| `committed` | 已确认数据库提交；若任务失败，失败发生在后续收尾 |
| `uncertain` | 提交或回滚结果无法确认，需要核验数据库 |

运行中不使用该字段宣称最终结果；非恢复任务为空。旧后端没有该字段时，前端保持未知，不因 `failed` 猜测已回滚。结果只保存在本轮进程内，不新增跨重启操作历史。

恢复启动响应还向发起客户端交付本轮随机 `restore_receipt`。客户端只在内存中保存它，通过 `X-Restore-Receipt` 读取该轮状态，并可在恢复结束后请求重启。恢复清空登录会话后，发起页面仍可读取结果。`restart_required=true` 表示服务保持维护状态，需要重启；它与 `completed`／`failed` 独立，不能据此推断恢复成功。查询失败保留已有进度并允许重试，不自动刷新页面丢失凭据。

恢复终态页面在 `restart_supported=true` 时提供“重启服务”，由用户主动调用 `POST /api/backup/restart`。接口只接受本轮有效回执及可信来源，要求恢复已明确成功或失败且需要重启；重复请求不重复执行。`restart_requested` 仅表示重启请求已接受，原恢复结果不被改写。准备重启失败时保留维护状态和结果，允许重试。页面等待服务重新上线后引导重新登录；服务上线本身不证明数据库恢复成功。不支持的环境保留手动重启提示，支持范围见[恢复后重启应用](deployment.md#恢复后重启应用)。

备份在文件写入、ZIP 收尾和完成记录保存全部成功后才进入 `completed`；目录创建、数据库操作、文件读写、压缩或异常退出都进入 `failed`。压缩或发布失败时清理本轮临时文件，已有同名 ZIP 始终保留。失败说明不包含内部路径或数据库细节，具体原因记录在服务日志中。备份和恢复的失败均不能仅靠 `is_running=false` 或 `count=total` 判为成功。

前端仅对明确的 `completed` 提示完成。连接旧后端时，仍在运行的任务继续查询；停止后若有 `error_msg` 则提示失败，否则提示结果尚未确认，停止查询并请用户核验记录和日志，不补猜成功。

## 恢复与风险边界

恢复只接受 ZIP，兼容 Store 和 Deflate 条目；可使用已有备份记录或上传文件。导出、上传与恢复遵守同一资源边界：

| 对象 | 上限 |
| --- | --- |
| ZIP 文件 | 1 GiB（1,073,741,824 字节） |
| 总展开内容 | 16 GiB |
| 单条 JSON 记录 | 64 MiB，包含解码边界间的空白；支持已有 17 MiB 大记录 |
| `manifest.json` | 8 MiB |
| ZIP 条目 | 4,096 个，包含目录 |
| ZIP 目录解析读取预算 | 8 MiB；这是读取预算，不是 Go ZIP 解析器的内存上限 |

上传在 multipart 解析前限制整个请求，允许文件上限之外最多 1 MiB 封装开销，并再次限制实际文件大小；超限返回 HTTP `413` 和顶层 `error_code=BACKUP_ARCHIVE_LIMIT`，清理暂存内容。解包前检查全部条目的路径、重复和文件／目录碰撞，拒绝符号链接等特殊文件；解包时再次限制实际读取量，不只相信 ZIP 声明大小。新格式只允许根目录清单、声明的表文件和必要目录；嵌套或大小写不符的清单直接拒绝，不能降级走旧包路径。完全无清单的旧包保留原表和一层包装目录兼容规则，但同样受资源和路径限制。

解压后先验证完整清单、版本、表／列、每行类型、行数和校验和，再进入维护。新格式要求与当前 schema 一致，支持 SQLite ↔ PostgreSQL 双向恢复；数据库不是任意第三方结构的通用转换工具。

恢复进入维护后，当前进程的数据库连接层拒绝新的普通操作，并等待已有语句、结果集和事务退出；恢复只使用持有维护许可的事务连接。HTTP 普通业务请求也被拒绝。该边界保护当前实例，不能协调另一个进程或外部 SQL 客户端，恢复前应停止所有共享数据库的其他写入方，并安排好网盘／文件操作的维护窗口。

删除旧表、重建全部结构、按依赖导入显式列值、清空浏览器会话、建立外键及必要索引、重建派生索引和重置序列都在同一个事务中完成，任一步失败回滚。恢复不通过模型创建钩子或默认值替换 `false`、`0`、空字符串或 `NULL`，也不调用会取消重复传输任务的去重修复。冲突数据会使整轮失败。清空 `user_sessions` 与恢复数据一起提交，旧包中的会话文件始终忽略；上传续传表不在此排除范围内。

Emby 派生索引从原收件、状态和不可变证据重建，不导入归档中的派生行。导入或重建失败时，旧数据库和旧索引一起回滚保留；不会把新旧数据混合后发布。字段和核验规则见[观察存储约定](../reference/database-schema.md#emby_webhook_recordsemby_webhook_targets)。恢复和清库仍使进程内同步位置缓存失效。

无清单的旧包采用单独兼容路径：要求可识别的数据库版本，支持当前版本及仅放宽文本列的 66→67 适配；更旧版本需先在适用程序中升级并重新备份。旧包缺少的无依赖表可保持现状，缺少将被替换父表的关联表则拒绝，避免破坏外键；这项依赖目标结构的检查在维护后的恢复事务内再次执行，防止预检后新增关联表使判断失效。旧程序未导出的字段无法凭空补回；API Key 缺少哈希、已启用两步验证却缺少密钥的包会在预检时拒绝。旧包的兼容导入不等同于新格式的完整性保证。

旧包中的同步扫描结果 `scan_result` 按 JSON 对象读取，恢复为数据库中的一层 JSON 文本；空对象仍是有效结果，`null` 或省略该字段时保留为 SQL `NULL`。

文本不会静默截断或替换非法字节。仍有业务长度约束的列会在导入前校验，超长或不能跨引擎表示的文本会报告表、行、列；不记录敏感字段内容。整数直接按整数编解码，不经过浮点数。Unix 秒保持原值；历史通知表的 `time.Time` 统一按 UTC、微秒四舍五入，SQLite 纳秒尾数不在跨引擎精度保证内。

一旦进入维护，无论事务成功还是失败，当前进程都保持维护状态直到重启，防止旧协程在恢复后回写。完整预检失败则不进入维护。正常导入失败会整体回滚；如果数据库连接在提交或回滚时异常，应根据日志核验最终结果。页面只有明确的 `completed` 才显示恢复完成，并保留成功或失败结果，由用户选择何时重启。重启会重新加载配置、缓存和持久任务。它是数据库全量逻辑恢复，不提供增量备份、时间点恢复或外部文件回滚。
