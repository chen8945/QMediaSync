## 独立配置与入口

“系统设置 → 媒体库”包含 Emby、Jellyfin 和飞牛影视三个标签。Emby 与 Jellyfin 各配置一台服务器，可以同时启用，分别保存连接、总开关、功能开关、选库、Cron、路径映射和同步状态。两端分别使用 `emby_config` 与 `jellyfin_config`；业务沿用原媒体表，以固定的 `media_server_type=emby|jellyfin` 隔离。来源存储类型与媒体服务器类型是不同概念。

新配置的 `enabled` 默认关闭。关闭总开关保留设置，阻止本端新的同步、刷新、Webhook 业务和提取执行；另一端不受影响。`enable_media_notification` 只控制本端媒体通知发送，关闭它不停止索引、提取或已授权的删除处理。`enable_extract_media_info` 只控制新增媒体的自动入队；手动“提取媒体信息”和已入队任务仍按总开关、原服务器身份和播放权限执行。

每轮业务读取并传递本端配置快照，普通查询必须携带合法类型；不能从全局 Emby 配置或当前 UI 标签推断归属。条目、成员、关联、版本屏障、收件、刷新目标和缓存均在本端范围内查询；已核验的父记录可向子记录传递归属。两端可以有相同远端 item/library ID，不能互相覆盖索引、同步水位或删除证据。物理来源锁和恢复维护门禁仍共用。

刷新／提取执行前的开关与连接检查只读取所需列，不解码无关路径映射。索引提交的配置摘要包含规范化映射，仍须完整读取配置并核验摘要，不能套用这类窄查询。

失败提取任务的重试调度仅核对本地总开关、来源、连接完整性、去重和重试上限，不同步访问媒体服务器。远端原 ServerID 和用户权限在提取执行入口核验，旧 URL 任务不能借用新凭据。关闭端保留任务且不消耗重试；远端失败沿用队列的有限重试。媒体服务器故障不能占住共享调度器，阻止另一端或普通下载入队。

共享下载队列在空闲时安排失败任务重试；查询或更新遇到临时数据库错误后，后续空闲调度仍可继续尝试，数据库恢复后无需新任务或手动操作才能恢复。读取任一端配置失败也按查询失败处理，不能当作该端未启用后报告重试成功；配置行不存在仍按未配置处理。成功安排任务才增加其重试次数，既有重试上限不变；成功且无可重试任务时，同一空闲周期不反复扫描。

连接与开关字段见 [配置说明](../operations/configuration.md#媒体服务器连接)，固定路由、读取／保存响应和省略字段语义见 [配置与提取请求](../engineering/request-validation.md#媒体服务器配置与提取)。保存允许离线操作，只更新配置字段，不覆盖并发同步状态。提交前失败保留原配置；提交后的应用失败保留已保存值并提示警告，同配置再次保存可重试应用。回读失败与应用警告分别展示。Emby 代理在本地应用后对后续请求采用新配置，无需重启；详见下节。

条目全量、增量和单项同步在准备期间遇到连接失败或配置变化时，也必须按固定入口收尾本端运行状态，保留错误且不推进成功水位。失败的索引令牌只保留本端类型，不授予提交资格；收尾入口拒绝空或非法类型，不能默认清理 Emby 状态。

### Emby 代理的配置与生命周期

Emby 302 模块拥有监听与连接会话。首次启用要求本端总开关、URL 和 API Key 完整，本地监听不等待远端产品或健康探测；监听绑定失败返回应用警告，同值重存可以重试。已有健康监听保持稳定，后续地址或密钥变化发布一个完整新会话；相同健康配置保存不重建会话。Jellyfin 配置不进入该模块。

每次 HTTP 请求和 WebSocket 握手捕获本次会话，连接、授权、路由、响应缓存和辅助请求均沿该会话执行。关闭总开关后，新请求在鉴权、缓存和预加载之前返回 `503`；已接受的 HTTP 流与已升级 WebSocket 保持原连接。HLS 的后续分片属于新请求。旧响应与旧授权只在原会话范围内可见，不能填入或命中新配置的缓存；响应缓存共用模块的一份容量预算。

换连接或关闭撤销旧会话的预加载，迟到响应不能恢复旧作业；已经接受的停止播放 Progress 辅助请求仍绑定原会话。模块复用不包含凭据的传输连接池，固定 OpenList／M3U8 资源及自定义脚本／样式缓存由模块拥有，网络读取和刷新沿模块的 TLS 策略与取消生命周期，在共享状态锁外完成。

最终停止先拒绝新准入，关闭监听和升级连接，取消请求、预加载与辅助后台，等待它们及缓存／M3U8 后台实际退出，再释放连接池中的空闲连接。超出停止期限时返回未退出错误，不能以关闭空闲连接代替取消和收尾；停止后迟到的应用不能复活模块。恢复维护许可覆盖已接受的请求和设置命令；WebSocket 成功升级后仅转发连接数据，释放数据库许可但保留会话引用，普通 HTTP 和辅助请求仍持有许可至完成。数据库替换仍遵守[恢复流程](../operations/database.md#恢复与风险边界)。证书、主站地址和内嵌策略保留启动时配置，见[配置说明](../operations/configuration.md)。

## Jellyfin 适用范围

Jellyfin 使用独立标签与原生管理接口，支持选库、手动／Cron 全量及增量本地索引、静态多版本、服务器已识别的分段、路径映射、同步后刷新、官方 Webhook 插件事件、媒体通知、主动提取和基于真实历史证据的联动删除。页面和播放访问 Jellyfin 本身；不提供 Emby 的 302、视频／字幕代理、页面脚本或 CSS 注入、代理响应增强及代理观察预加载。

客户端位于 `internal/medialibrary/client`，共用传输与分页，`emby.go`／`jellyfin.go` 封装协议差异。只需判断产品时请求 `/System/Ping`；业务需要真实 ServerID 时按需请求 `/System/Info/Public`，复用明确产品，Public 未识别时补 Ping。Ping 支持 Emby 的纯文本与 Jellyfin 的 JSON 字符串标识。反向代理子路径保留，只有明确 404 才尝试 Emby 前缀；不按版本分流，不因原生业务请求失败自动切换协议。

明确识别为另一产品的连接不能执行本标签业务，Jellyfin 不能接入 Emby 代理。产品探测失败保留“未确认”及诊断、不缓存失败，也不单独阻断既有业务；最终未知产品沿用原 Emby 协议。需要身份、详情或用户权限的操作仍须完成实际业务核验。并发合并 Ping 或 Public 探测时，发起者取消或超时不会使其他有效请求失败；等待者按自己的上下文重新探测，自身取消则及时退出。Emby 代理启动不等待远端探测，远端暂不可用不阻止本地监听；后续请求重试核验。代理配置与旧请求的边界见[Emby 代理生命周期](#emby-代理的配置与生命周期)。

Jellyfin 使用原生管理路由及 `Authorization: MediaBrowser … Token="…"`。Items 显式请求 `DateCreated,ParentId,Path,MediaSources`，分页按 `DateCreated,SortName` 排序，增量使用 `MinDateLastSaved` 和 600 秒重叠窗口；成功游标取扫描起始时间。总数变化、重复身份、提前空页或不完整组失败时不清旧、不推进成功水位。该分页机制不提供远端事务快照。

Jellyfin UUID 在分页去重前规范化为 32 位小写非零值。静态 `MediaSources[].Id` 经来源类型和条目归属核对后补入既有 `ItemID`，来源自身的 ID 和播放 URL 保留原义；Grouping 版本可关联，频道与占位来源不推断物理归属。数字 Emby 保留原数值稳定根，Jellyfin 版本组按规范化 GUID 取稳定根，不按标题合并。分段使用 AdditionalParts；缺详情、缺成员或跨组冲突使整组失败。

合集库通过 `CollectionType=boxsets` 从两端共用的媒体库入口排除；Jellyfin 系统播放列表集合还通过 `Type=ManualPlaylistsFolder` 或 `CollectionType=playlists` 排除。这些逻辑集合不参与 QMediaSync 的选库、索引或媒体信息提取，其中引用的影片仍通过原电影或电视剧库处理。普通媒体库即使同名为“合集”或 Playlists 也保留，不按名称、普通 `CollectionFolder` 类型或目录列表是否为空过滤。

查询媒体库得到完整成功的空 `Items`，或排除逻辑集合后已无普通媒体库时，清理当前端的 `emby_libraries` 缓存及 `emby_library_sync_paths` 关联，并返回空列表；另一端的库和关联保留。失败、缺失/null `Items` 或损坏响应不触发清理。非空清单只清理已不在本端清单中的库，媒体条目、同步配置和持久任务不扩大级联；清理数据库失败仍返回 `200`、成功清单和顶层 `warnings`。Emby/Jellyfin 设置页保留清单并展示清理警告，保存后刷新追加警告且保留已保存说明和原应用警告；请求失效边界见 [前端开发](../engineering/frontend-development.md#媒体库设置)。

STRM 原生 HTTP 来源直接使用。Jellyfin 返回本地 STRM 来源时，先有界补读有权限用户的同一条目详情，核对条目类型、实际路径和来源归属；仍未提供 URL 的受管 STRM，利用已有同步文件与可信路径对应只读本地内容，再交给现有来源及账号身份解析。不会访问播放 URL、查询网盘或根据文件名猜测身份；正常原生来源不产生这类补读，也不按 Jellyfin 版本分流。该兼容只补足 QMediaSync 的来源关联，不修改 Jellyfin 数据库或修复其媒体探测。

已精确识别的受管 STRM 若读取失败、内容与账号或文件标识不符，普通同步不提交该组，保留原有正确关联并报告失败。删除前的完整本端存活清单也复用来源兼容，以识别另一路径或新条目 ID 对同一云盘文件的引用；已确认受管但来源未能恢复时，本次删除核验失败，不发送网盘删除请求，也不把通知标记为删除处理成功。即使该存活条目的新 ID 尚未入索引，也不能仅凭本地路径位于待删目录外就断言云端文件无关。原生 HTTP 来源及可正常恢复的 STRM 继续按实际来源判断共享关系。

合并后的隐藏版本可能不出现在 `Items?Ids=...`，通过具备全部媒体库权限的用户调用 `Items/{id}?UserId=...` 补查详情。隐藏版本只声明自身来源时，按完整主项声明核对成员；冲突或缺详情仍使整组失败。公共详情、图片和通知用户查询保留原全部媒体库权限规则，`EnableMediaPlayback` 只用于提取候选用户。

Jellyfin 不使用 Emby 远端 `Path` 查询；刷新按本端本地 item、同季／同剧及媒体库关联解析。原生 `POST /Items/{id}/Refresh` 设置 `MetadataRefreshMode=Default`、`ImageRefreshMode=Default`，不发送 Emby 的 Fields／Recursive，不强制替换元数据。HTTP 成功只表示已接受任务，新增剧集和图片是否生效需观察服务器扫描结果。官方插件及删除边界见下文；GUID 本身不构成删除授权。

## 两条链路

每端均有两条独立链路，不能混用。后文保留原 Emby 模型与函数名；公共调度入口按类型分别处理启用的 Emby、Jellyfin。

### 链路 A：通知媒体服务器刷新

含义：QMediaSync 通知本端媒体服务器刷新已有 item 或重新扫描它自己的媒体库。

刷新功能需要满足以下前置条件：

- 本端总开关已启用，已配置 URL 和 API Key，并启用 `enable_refresh_library`。
- 刷新来源必须属于已保存的同步目录，临时同步目录不提交刷新。
- 建议先完成一次本端链路 B 的条目同步，用于建立 `emby_media_items`、`emby_media_sync_files` 和 `emby_library_sync_paths` 关联。没有 item 关联时会尝试回退媒体库刷新；同步目录也没有媒体库关联时会跳过提交。

#### 当前有效入口

| 入口 | 上游触发方式 | 提交条件 | 提交函数 |
| --- | --- | --- | --- |
| 常规 STRM 同步 | 全局同步、单同步目录同步、115 全量同步、全局或目录自定义 Cron、Telegram `/strm_inc` 和 `/strm_sync` | 非临时同步目录成功完成，且新增 STRM 或新增元数据下载任务 | `models.RequestMediaLibraryRefreshTargets(...)` |
| 上传完成后的 STRM 生成 | 目录监控上传完成、STRM 上传完成或远端文件已存在 | 非 Webhook 文件任务的 STRM 实际新增或更新 | `models.RequestMediaLibraryRefreshTargets(...)` |
| STRM Webhook | `POST /api/strm/webhook` 的单文件、批量文件或目录扫描请求 | 显式设置 `refresh_emby=true`，并且 STRM 发生变化或新增元数据下载任务 | `models.RequestMediaLibraryRefreshTargets(...)` |

常规 STRM 同步包括以下管理入口：

- `POST /api/sync/start`：把符合条件的同步目录加入队列。
- `POST /api/sync/path/start`：启动单个同步目录。
- `POST /api/sync/path/full-start`：启动单个 115 同步目录的全量同步。
- 全局同步 Cron 和同步目录自定义 Cron。
- Telegram `/strm_inc`、`/strm_sync`。

`new_meta` 表示已创建元数据下载任务，不表示元数据已经下载完成。常规同步完成后先提交刷新任务，刷新协调器再等待这些下载任务结束。目标已冻结真实 ServerID 时，提交前核验本地索引归属即可持久入队，不以媒体服务当前在线为前提；服务离线时保留原目标，恢复后由协调器核验远端真实实例再执行，无需再次生成文件。缺少 ServerID 的目标仍须先取得真实身份，不能离线补造。

`POST /api/sync/manual` 使用临时同步目录，不提交 Emby 刷新任务。

上传完成、远端已存在等非 Webhook STRM 任务由 `strm_generation_tasks` worker 处理。只有 STRM 内容实际变化时才提交刷新；STRM 内容不变时只确认或更新 `sync_files`，不创建新的刷新任务。普通上传在写入前冻结目标，可复用与当前连接对应的本端索引中已确认的真实 ServerID；媒体服务暂时离线时仍可生成 STRM，持久提交失败则保存原目标并等待重试。新连接没有可靠原身份且远端身份查询失败时，只在确有待写变化时中止，恢复后可重新提交。提交时保留并核对原目标的本地归属，执行前校验远端真实实例，不把旧连接的索引身份用于新连接。

完整同步在 STRM 写入成功并释放目标锁后收集刷新目标，解析失败仍记录告警并回退媒体库目标。单文件后处理由服务按任务来源处理刷新，不在底层写文件时重复解析；写入后的提交失败保存原目标，进入既有收尾重试。两条入口都等待自己负责的刷新处理结束，提交成功不代表 Emby 已扫库完成。

STRM Webhook 的具体规则：

- `refresh_emby` 保留历史字段名、默认关闭，调用方必须显式设置为 `true`；它分别向本端总开关与刷新开关均开启的 Emby／Jellyfin 提交。
- 单文件任务只有在 STRM 变化或新增元数据下载任务时提交刷新。
- 批量文件和目录扫描先由子任务累计刷新目标。
- 只有父任务全部子任务成功、计数满足且存在 STRM 或元数据变化时，才统一提交一次刷新。
- 任一子任务失败时父任务失败，不提交父任务累计的完整刷新集合。

请求刷新的 Webhook 文件任务在产生 STRM 或元数据变化前先解析并冻结各启用端的类型和真实 ServerID；解析失败不先写入这些变化，修复连接后可重新提交，避免重试时把已写入文件误判为“无变化”而丢失刷新。没有 STRM 变化，且元数据无匹配项、本地已存在或已有同目标的活跃下载时，不会仅因解析失败而阻止完成。写入后独立任务的刷新提交失败会保存目标并进入 `finalizing`，恢复时只重试原目标，不重新生成；批任务仍由父任务累计目标、子任务收尾重试。两端提交分别处理，单端失败不阻止另一端已冻结目标入队。首次提交和收尾重试均按端保存进度：现有目标 JSON 仅保留尚未成功提交端的原目标，全部完成后置已提交；独立文件和批任务均在重载后只重试剩余端，避免每 5 秒重提健康端而反复推迟其 10 秒防抖时间。新的 STRM 或元数据变化仍正常重设刷新防抖，去重、等待和实例身份核验保持。普通无变化任务不新增刷新。

刷新提交时，配置读取失败会返回该端错误，收尾任务保留该端原目标并在数据库恢复后重试；其他端可继续提交。配置不存在、连接信息不完整或已明确关闭刷新时，仍按原规则跳过。读取失败不能当作关闭，也不能据此清空待办目标或标记已提交。

升级或恢复备份后，STRM 批任务持久目标缺少 `MediaServerType` 时，仅在历史读取边界按 Emby 解释；显式类型保持原值，公共刷新入口仍要求合法类型。关闭刷新时旧任务可以正常收尾；开启时仍核验真实服务器身份和当前索引，不将旧目标发送给 Jellyfin。

#### 当前不是刷新入口的功能

- 两端的 `/api/{emby|jellyfin}/sync/start`、条目同步 Cron 和 `/{emby|jellyfin}/webhook` 属于链路 B，只维护 QMediaSync 本端索引，不调用刷新接口。
- 前端当前只有“同步后刷新媒体库”开关，没有“立即刷新媒体库”按钮，也没有独立的刷新 API。
- `models.RefreshEmbyLibraryBySyncPathId(...)` 是直接请求 Emby 的旧函数，当前没有生产调用方；当前刷新统一经过任务协调器。
- Telegram `strm_scrape` 对应的同步、刮削后刷新代码仍存在，但命令注册已注释，不属于当前有效入口。
- `refresh_library` 状态值已经在后端常量和前端文案中定义，但刷新协调器当前不会设置 `emby_config.sync_mode`，因此 `/api/emby/sync/status` 不展示刷新任务的实际运行状态。

#### 统一运行流程

```text
常规 STRM 同步 / 上传后处理 / STRM Webhook
                    │
                    ▼
            按本端解析刷新目标
            item 优先，媒体库兜底
                    │
                    ▼
    创建或合并 emby_library_refresh_tasks
            task_key 去重 + 10 秒防抖
                    │
                    ▼
      等待相关 STRM 同步和下载任务结束
                    │
                    ▼
       按本端 item 或媒体库调用 Refresh API
```

完整流程如下：

1. 上游任务确认存在 STRM 或元数据变化。
2. 调用 `ResolveMediaLibraryRefreshTargets(...)` 分别解析启用端的 item 或媒体库目标。
3. 调用 `RequestMediaLibraryRefreshTargets(...)` 提交已冻结目标；旧固定 Emby wrapper 保留，公共入口不省略类型。
4. 创建或合并 `EmbyLibraryRefreshTask`，将任务状态设置为 `pending`，刷新时间设置为最后事件时间加 10 秒；提交后协调器会重新检查所有 pending 任务。
5. 全局 timer 指向最早的 `pending.refresh_after_at`，到期后唤醒协调器；60 秒 ticker 作为兜底扫描。
6. 协调器先按真实媒体库归并 pending item，再逐条判断同步目录和下载队列是否稳定。
7. 满足条件后原子地把任务从 `pending` 改为 `refreshing`，防止同一任务并发执行。
8. 调用 Emby item 或媒体库刷新接口，并将任务标记为 `completed`；请求失败时标记为 `failed`。

#### 刷新目标解析

刷新目标按以下顺序解析：

1. 根据 `sync_file_id` 或 PickCode 查询本地 `emby_media_sync_files` 和 `emby_media_items` 关联。
2. 已有关联的 Movie、Video、Episode 刷新对应 item。
3. 同季新增剧集没有自身 Episode 关联时，按同步目录和路径查找同目录 sibling Episode，只检查最新的 50 条记录并排除自身。优先刷新 Season，缺少 Season 时刷新 Series。Season、Series 和 Folder 使用递归刷新。
4. 本地索引无法定位 item 时，Emby 按 STRM 本地路径请求 `/Items?Path=...` 做一次兜底查询；Jellyfin 跳过此查询。
5. 路径查询命中后，优先采用本地 item 或 sibling Episode 的媒体库证据；必要时通过 Emby Ancestors 消歧，最后才使用同步路径唯一关联的媒体库。
6. 仍无法定位可靠 item 时，回退同步目录关联媒体库刷新。

远端 Ancestors 解析按 Emby 服务、凭据和 item ID 缓存 30 秒。同一 item 的并发解析会合并为一次请求，远端失败结果不缓存。

item 级刷新目标使用 `item:<item_id>`，媒体库刷新目标使用 `library:<library_id>`；持久任务以 `(media_server_type, server_id, task_key)` 去重，不能按相同目标 ID 合并不同端或实例。原 ServerID 为空的旧任务不补造身份，扫描时取消并要求重新提交；当前 ServerID 改变也取消，同端同 ID 可轮换当前地址／密钥执行。`library_id` 只保存真实媒体库 ID 或为空；`fallback_library_id` 只保存当前解析出的有效媒体库或旧任务 hint。解析优先级为本地 item、Season/Series sibling Episode、Emby Ancestors、同步路径唯一关联媒体库和仍属于候选集合的旧 hint。多库且没有可靠证据时保持 unresolved，不会任选第一个媒体库。某组即将被已有 pending library 吸收或达到阈值转换时，协调器会在同一个聚合事务中使用当前本地索引重新校验该组 hint；如果本地 item、sibling Episode 或唯一同步目录给出更强证据，会先修复持久化归属，并把归属变化的 item 留到重新分组后再处理。该校验不会调用 Emby HTTP API，本地没有更强证据时保留可能来自 Ancestors 的旧 hint。未达到吸收或转换条件的普通 pending 组不会执行逐 item 复核，避免连续提交时产生重复全量查询。

刷新解析保留旧 item／同季同剧条目的原 ServerID，并与本端索引状态和当前实例核对；不一致时拒绝新绑定，不能把旧索引重标为新实例。旧 pending 任务的媒体库回退复核也限定原 ServerID，不能用新实例关联改写。关闭总开关不暂停刷新任务的原绝对截止时间。

批量目标会在提交前去重。通用 library fallback 会先展开为同步目录关联的精确 `library:<library_id>` 目标，再覆盖同库 item；不同媒体库的目标互不影响。

目标解析结果需要区分两类 unresolved：

- 完全无法定位 Emby item 时返回通用 library target。该目标会展开为同步目录关联的全部媒体库，library fallback 优先于 item 数量阈值。
- 已找到 item ID，但无法确定所属媒体库时，保留 `item` target 且 `fallback_library_id` 为空。这类任务不参与任何媒体库阈值统计，也不会根据同批次其他 item 猜测媒体库。

#### 媒体库级 pending 聚合

聚合阈值固定为 `10`，统计同一个真实 `library_id` 在滚动防抖窗口内的唯一 pending item 任务。滚动窗口不是固定时间桶，组级结束时间为：

```text
group_refresh_after_at = max(组内所有 pending item 的 refresh_after_at)
```

因此该规则同时覆盖单次批量提交、不同入口和不同批次产生的任务。新 item 或相关下载事件会延长整个媒体库组的稳定窗口。

协调器按以下优先级处理：

1. 已有 `pending` 的精确 library 任务时，无论 item 数量是否达到 10，都吸收同库 pending item。
2. 没有 library 任务且防抖窗口尚未结束时，保持 item 任务，并将组内 `refresh_after_at` 同步为最大值。
3. 防抖窗口结束后，少于 10 个 item 保持 item 刷新。
4. 达到 10 个或更多唯一 item 时，创建或更新精确 `library:<library_id>` 任务，并将被覆盖的 item 标记为 `cancelled`，保留取消原因用于审计。

聚合、字段合并和 item 取消在同一个数据库事务中完成。事务开始时先取消已经过期的 pending 任务，再查询有效 pending item；过期任务不会参与阈值，也不会被当作有效 pending library 重新使用。`last_event_at` 和 `refresh_after_at` 取最大值，`deadline_at` 取最早有效值，`sync_path_ids` 取并集；不会因为合并重新获得完整的 6 小时等待时间。已有 pending library 会保留当前周期的 `item_ids` 并继续合并；completed、failed、cancelled 或已过期任务进入新周期时会清空历史 `item_ids`，避免任务负载随媒体库生命周期持续增长。

聚合查询只读取有效 pending item 和这些 item 对应的 library 任务，不加载 completed、failed 或 cancelled 的全部历史记录。活动周期内新增同步目录或新事件不会重置原有 deadline；只有新任务或 terminal 任务重新激活时才创建新的最长等待时间。

并发控制按数据库类型采用混合策略：PostgreSQL 在事务内按固定顺序锁定 library 和 item 行；SQLite 使用进程级 Emby 刷新任务写锁配合短事务。两种模式都保留 `status` 条件更新和唯一 `task_key` 约束，状态领取前会重新确认任务仍已到达防抖时间，避免旧扫描提前刷新新事件。并发创建同一个 `library:<library_id>` 发生唯一键冲突时，当前事务会重新锁定已有任务、重新合并字段并保存；只有保存成功后才取消被吸收的 item，保存失败则整体回滚。

扫描器不会把读取到的旧任务整行写回。readiness 检查出错或任务暂不可执行时，只在任务仍为 `pending`，且 `last_event_at`、`refresh_after_at`、`deadline_at` 与扫描快照一致时更新 `last_checked_at`；检查出错时同时更新 `error`。如果期间有新事件或状态变化，条件更新不命中，旧检查结果直接丢弃。deadline 到期取消同样要求数据库中的 `deadline_at` 与旧快照一致且仍已过期；新事件已续期时，旧扫描不能取消新周期任务。SQLite 进程锁只覆盖对应的单条条件更新，PostgreSQL 依靠原子 `UPDATE ... WHERE ...` 保证该语义。

SQLite 刷新任务写锁假设同一个 SQLite 数据库文件由单个 QMediaSync 进程写入；如果未来需要多进程共享写入，应切换到 PostgreSQL 或单独设计跨进程事务协调。

正在 `refreshing` 的 library 任务不会吸收新 item，新 item 留到下一轮。刷新完成或失败时使用 `status=refreshing` 条件更新，避免旧请求覆盖并发事件重新排队形成的 pending 任务。

典型边界结果：

| 输入 | 结果 |
| --- | --- |
| 8 或 9 个同库 item | 保持 item 刷新 |
| 10 或 11 个同库 item | 合并为一个 library 刷新 |
| 9 个 lib-a item + lib-a fallback | 只保留 `library:lib-a` |
| 9 个 lib-a item + lib-b fallback | `library:lib-b` 加 9 个 lib-a item |
| 9 个 lib-a item + unresolved item（无库归属） | 9 个 lib-a item 加 1 个 unresolved item，不触发阈值 |
| 同步目录同时关联 lib-a、lib-b 的通用 fallback | 分别创建两个 library 任务，不按多数归属选择一个 |

此前“通用 library fallback 与同库 item 同时存在”的重复刷新问题由两层逻辑解决：提交批次先展开并归一化精确 library target，协调器再对数据库内所有 pending 任务做跨批次聚合。

#### 协调器等待和调度

停止协调器时，各端执行分支在处理下一条任务前检查停止信号，不继续执行已读批次的剩余待办。已开始的单条任务按原请求超时和状态规则收尾，停止等待其退出；未执行任务保留原状态，重新启动后继续正常检查。

每个任务独立维护以下时间：

- `last_event_at`：最近一次相关变化时间。
- `refresh_after_at`：允许再次检查的时间，默认是 `last_event_at + 10 秒`。
- `deadline_at`：最长等待时间，默认是首次事件后 6 小时。
- `last_checked_at`：协调器最近一次检查时间。
- `last_refresh_at`：最近一次成功请求 Emby 的时间。

协调器判断任务 ready 时会检查：

- 任务必须为 `pending`，并且已经超过 10 秒防抖窗口。
- 等待范围始终包含任务自身 `sync_path_ids`。
- 根据可靠媒体库证据解析到媒体库后，还会扩展到该媒体库关联的其他同步目录。
- 等待范围内不能有处于等待或运行状态的 STRM 同步任务。
- 等待范围内不能有 `pending`、`downloading`，或失败但仍可自动重试的下载任务。

下载任务状态变化会先按同步目录或 `sync_file_id` 收集，每 5 秒批量更新相关刷新任务的 `last_event_at` 和 `refresh_after_at`，避免大量小文件频繁触发数据库查询。下载队列确认没有待下载和下载中任务后也会主动唤醒协调器。

用户清空等待下载任务时，系统会同时取消受影响同步目录的 `pending` 刷新任务；暂停下载队列和重试失败任务不会取消刷新任务。

如果等待超过 6 小时，任务转为 `cancelled`，不会强制刷新仍有同步或下载任务的媒体库。服务重启时，遗留的 `refreshing` 任务会恢复为 `pending`，重新进入 10 秒防抖窗口。

刷新任务创建、更新或下载事件批量落库后，会把全局最近到期 timer 调度到最早的 `pending.refresh_after_at`。并发调度时，较旧的数据库查询结果不能取消或覆盖已经存在的更早 timer。全局 timer 只负责唤醒检查，不直接决定是否刷新；每条任务仍独立判断是否 ready。

#### 执行和失败回退

任务状态流转如下：

```text
pending → refreshing → completed
                    └→ failed
pending ─────────────→ cancelled
```

item 刷新失败后，系统会重新根据本地 item、sibling Episode 和同步路径关联解析真实媒体库，并按需请求 Ancestors。只有成功解析出唯一媒体库时才回退媒体库刷新；仍为 unresolved 时保留原始失败结果，不会刷新不确定的媒体库。

- item 定向刷新接口：

```http
POST /emby/Items/{itemId}/Refresh?Recursive=<true|false>
```

- 媒体库刷新接口：

```http
POST /emby/Items/{libraryId}/Refresh
```

职责边界：

- 只调用 Emby 刷新接口。
- 不拉取 Emby item。
- 不写入 `emby_media_items`。
- 不建立 PickCode 和 `sync_files` 关联。
- 不和链路 B 串成一个长任务。

### 链路 B：同步媒体条目到本地

含义：QMediaSync 从 Emby 拉取媒体条目，写入本地数据库，用于建立 Emby item、PickCode 和同步文件之间的关联。

触发场景：

- 手动全量同步。
- Cron 定时增量同步。
- Webhook 新增或修改事件触发单条同步。
- 低频全量校验或重建本地索引。

职责边界：

- 只维护 QMediaSync 本地索引。
- 不调用 Emby 媒体库刷新接口。
- 不等待 STRM 生成流程。
- 不把“通知 Emby 扫库”和“同步 Emby 条目”串成一个长任务。

前端状态文案：

| 状态值 | 展示文案 |
| --- | --- |
| `idle` | 空闲 |
| `full` | 全量同步 Emby 条目 |
| `incremental` | 增量同步 Emby 条目 |
| `webhook` | Webhook 单条同步 Emby 条目 |
| `refresh_library` | 刷新 Emby 媒体库（预留状态，当前协调器不写入） |

## 同步架构

推荐运行模式是“Webhook 实时单条处理 + 定时增量兜底 + 低频全量校验”。

### 分页流式处理

全量同步和增量同步都复用分页拉取逻辑：

- 每页 `Limit` 默认取 `100`。
- 一个枚举者分页读取完整物理组，不把全部媒体项聚合成一个大切片。SQLite 使用两个准备 worker、一个按枚举顺序提交的调用方，总在途最多 `4` 组；提交时非阻塞收取已准备好的独立组，每批最多 `4` 组。
- PostgreSQL 将三个准备 worker 与三个提交 worker 解耦；就绪队列容量为 `8`，排队、准备、等待许可、提交及已提交但尚未确认的组总数最多为 `24`。每批最多合并 `4` 个独立物理组，凑批最多等待 `1` 毫秒，尾批及时提交。
- PostgreSQL 只让独立普通组并行提交；已有成员关系或本轮版本、分段等复杂组保留前后屏障及输入顺序。任一组失败使该批事务整体回滚，其他批次已经提交的结果仍须回收。worker 数不改变现有可配置连接池上限，连接设置见[数据库运维](../operations/database.md#引擎与初始化)。
- worker 在本轮媒体库内按父项、季剧身份及真实父路径共享 Emby 祖先观察，同目录并发读取合并，不同目录仍可并行。观察自真实读取完成起有效 `30` 秒，命中不续期；普通读取失败也在此窗口内复用，取消不缓存失败。缓存不含电影条目身份，应用时逐条绑定；本地目录账本缓存继续由各 worker 独占，提交仍重新核对当前身份。
- 每个物理 item 保存 Item.Path 与媒体源播放路径，保留来源 Id／ItemId；成功快照与当前关联替换在同一事务完成。所有来源都参与核验，不能确定物理归属的多来源响应返回错误。
- 主项、版本和分段整组进入原有事务；协调者独占去重及计数，已经被前组覆盖的外层条目跳过整个预取组。准备、分页或提交失败时保留触发取消的原始错误，等待在途工作退出并收齐已成功提交的结果；失败库不清旧、不推进成功水位。不在数据库事务中请求远端。
- 不再对每个 item 固定 sleep；如需限速，应限制分页请求频率或使用可配置限速。

### 本地文件和目录资料

普通全量、增量、单条同步及 Webhook 早期观察读取本端媒体信息和必要的本地 STRM，不主动查询网盘，也不安排后台网盘预采集。全量与增量完成日志保留当前处理量和耗时文案，并追加“网盘查询 0 次”。文件身份和根下目录关系复用 `SyncFile`；115 同步根及根外祖先由[正常 STRM 同步](sync-orchestration.md#生成结果与后台账本)保存。目录信息只随已确认的同步结果更新，不以固定时间清空。

Emby 的全部来源、实际 STRM 路径和 Movie／Season／Series 媒体目录角色独立保存；没有文件关联时也保留已知信息。Windows／UNC 的原始媒体路径按 Emby 路径规则处理，不受 QMediaSync 所在系统的路径格式限制。已经证明的物理目录链、有效同步根及媒体角色在本地组合成目录范围，再按原规则冻结普通附件和季海报。季海报查询在 SQL 内限定来源、账号、目录及文件名，同时核对 Season、Series 和季号。准备期文件与事务中冻结的文件必须一致，不能将旧目录观察绑定到新的文件身份。

Jellyfin 将电影物理文件夹从原生祖先树中省略时，已确认关联的受管 `SyncFile` 可提供电影父目录角色，记为 `jellyfin_managed_movie`。本地文件与同步根的路径对应、账号主体、云端目录稳定身份链仍须成立；无需先执行刮削。仅有任意条目路径、外部未关联 STRM 或同步根本身不产生该资格。Movie 的目录角色随后复用现有目录计划、完整本端存活清单和共享成员保护；Season／Series 继续使用真实祖先角色。新同步形成的新证据不回写旧收件的冻结授权。

每组提交仍在原事务内重新核对当前根链及涉及的目录：按稳定对象 ID 检查移动或改名，按原父路径与名称检查同名替换。名称查询使用[同步文件索引](../reference/database-schema.md#sync_files)缩小读取范围，不以准备期缓存代替提交校验；账号、同步根和路径表示的原有隔离规则保持一致。

SQLite 将目录身份与路径／名称候选分开读取，稳定身份逐 ID 等值查询，再按记录 ID 合并、去重和排序；百度目录仍按 `pick_code` 核对身份。旁车仍在同来源、同账号的目录内匹配，允许跨同步根，不能为了索引命中缩小原有匹配范围。PostgreSQL 保留自己的查询形态与长路径 HASH 索引。

升级后的本地组合可以复用仍与当前状态、服务器连接、账号主体、根和文件身份匹配的旧目录证据；只改变选库范围不会使有效物理链失效。只读取当前有效快照，不扫描全部历史或把提交时间当作网盘读取时间。明确失效或冲突的根资料不能经旧快照回退重新生效。缺少可证明的资料与数据库读取失败分别处理：前者保留独立已知信息，后者使本轮失败，不能以空证据覆盖有效旧状态。

完整数据的验收从空库开始：正常 STRM 响应完成文件及目录资料落库，重启后执行 Emby 同步，仍能构建文件、目录、附件和季海报证据。已有库含旧预采集资料，不能代替这条冷启动验证。115 的完整祖先链能力不等同于百度或 OpenList 的接口能力。

### 外部 STRM 来源和路径映射

Emby 返回的来源继续作为媒体来源依据，唯一、可靠的已有文件绑定优先。来源类型、可确定的账号主体和稳定对象键在 URL 脱敏前单独保存；相同 PickCode 或重复来源 ID 仍须按对象和账号分别匹配，不能串用绑定或丢弃未绑定来源。账号不明或多候选冲突时保留原因，不能遍历账号试探。实际 STRM 引用路径与 QMediaSync 管理路径分别冻结，不能覆盖其中一个来制造路径相等。

QMediaSync 生成和外部 STRM 共用自动路径推导：从已确认的本地存放根与 STRM 路径计算完整相对路径，再与 Emby 路径按组件比对，确认只差挂载前缀时保存该条目的对应关系。Windows／UNC 与 POSIX 分别遵循原有路径语义，不使用普通字符串后缀匹配跨目录。一个条目即可确定自身对应，不能把它推定为所有未知文件的根映射。

已有文件绑定直接复用本次读取的路径和根。没有文件绑定且没有明确映射时，在事务外从同来源、同账号的已知 STRM 同步根中尝试有限个候选路径，只读符合条件的本地 STRM 并核对来源；不递归枚举磁盘、不访问播放 URL、不请求网盘。准备期复用本轮所需的同步根，提交只复核原定位依据，不在事务中重新搜索文件。已有明确映射或可靠绑定不新增强制读取 STRM 内容的前提，外部文件内容始终不改写。

自动引用随原快照保存定位根及账号依据；目录的本地访问根与网盘结构归属分别表示。外部文件仅被自动定位时，不因此填写用于目录归属的 `sync_path_id`，也不新增历史网盘目录权限。已有受管文件的结构对应仍须结合原文件、根链及媒体角色核验。重新同步可以保存新对应，旧删除通知只核对冻结路径和原依据，根、账号或明确映射变化后不能改用后来找到的位置。

`path_mappings` 沿用 Emby 配置接口，手工入口暂不挂载，具体字段和校验见[配置说明](../operations/configuration.md#emby-外部-strm-路径映射)。已配置的明确规则优先，不能通过自动推导绕过其冲突或变化。`emby_root → local_root` 表示文件系统访问映射；手工选定的 `sync_path_id` 另行声明相对媒体目录结构，仍需核验真实目录身份。映射随来源快照冻结，执行时核对原映射仍成立；手工映射进入索引配置摘要，空映射兼容旧摘要，不改变服务连接身份。自动引用不写回用户配置，普通设置保存省略映射字段以保留现有值。

实际删除按已有资料优先处理。完整文件身份不增加身份补全请求；已确定来源和账号、但缺少物理身份的选中来源才按需补查。115 已有 FileID 时直接复用必要详情或清单，只有可信账号和 PickCode 时才使用 `downurl → get_info(文件 ID)`；完整响应和目录清单供后续核验共同使用，不逐层查询祖先或逐文件重复已覆盖的读取。百度按 fs_id 定位，OpenList 保留既有详情与完整清单的交叉核验。

补充资料关联本次计划、原来源和快照，保存真实读取时间，不覆盖原输入或历史 `files_json`。没有 `SyncFile/SyncPath` 的目标使用独立来源校验，不伪造文件记录或同步根。只有稳定对象绑定而没有历史内容指纹时，保证限定为同一个稳定来源对象，不证明其内容自同步后未变化。多个引用补全为同一物理对象后仍分别核对存活使用者，全部属于本次可删除范围时才只执行一次物理删除。

明确的账号、映射或来源身份冲突按来源保留原因及关联条目，其他独立核验通过的来源继续。临时来源定位失败沿用原通知最多四次处理机会：前三次按原退避重试，不保存残缺计划；最后一次将成功补证和失败来源原因一起保存，再执行健康目标。计划保存后，重启不重建补证或已完成结果；重试时经数据库确认某目标账号缺失或主体变化，保留该目标并记录结果，其他账号仍可继续。不能只凭 provider 返回错误认定账号冲突，账号仍一致或数据库复核失败时仍返回原错误。服务器、原快照、无法确定影响范围的核验错误及取消仍中止整轮；来源隔离不放宽原有目录清单准入。

准备日志按原因汇总保留来源数量，用中文区分账号变化、映射变化、身份冲突和补查机会耗尽，不逐来源刷日志。“四次处理机会”不是四次 HTTP 请求，分页、必要核验和客户端重试另计。

文件身份补全不产生历史整目录权限。整目录清理仍须同时证明原媒体归属和原目录对象，保留同步根、其他使用者、目录移动及替换保护；无法访问挂载根不能视作 STRM 已消失。补查结果的执行期复用受原范围、账号、读取时间和变化规则约束，115 写入后已有读取缓存失效，写后确认必须使用新的响应。最终发送检查只消费已准备且仍有效的资料，不能在 115 队列回调内再次排读取。

### 物理快照与身份版本

Emby 同步显式请求 Path、MediaSources、PartCount 及季／剧上下文字段；Jellyfin 只请求其支持的 Fields，其余上下文字段按 DTO 返回读取。Movie 和 Episode 的 PartCount>1 时请求 `/Videos/{id}/AdditionalParts`，保留隐藏 Video 与主项关系；已有完整字段直接保存，主项、版本和分段缺 Path／MediaSources 时才按 ID 补详情；补查后仍缺字段则保留旧快照。分段读取失败时主项和分段均不替换，当前关系保留。

物理 `/Items` 枚举不会按名称或 TMDB ID 合并版本。额外来源明确指向其他 ItemId 时查询其物理详情，再独立建立关联；无 ItemId 的多个不同来源不会盲绑到外层条目。没有云端来源的完整响应仍保存媒体项并清除旧关联。快照更新允许空字符串、0 和 false，保留 CreatedAt；增量与单条同步不清全量批次标记。

每轮远端条目读取前核验 `/System/Info/Public` 返回的实例 ID，获取持久版本。四个索引入口（全量、增量、单条及旧单条兼容函数）都使用同一事务提交，并核对配置范围和版本。数据库删除屏障登记、提交和成功游标／时间水位使用同一 SQL 锁；空扫描也核对版本。旧查询在屏障释放后仍会被拒绝，普通 UpdatedAt 不能替代代际。配置快照只属于本端及当前批次；设置页读取最新配置，保存只更新配置字段，不回写同步期间变化的游标／运行状态。服务地址、授权或有效选库范围改变时清除旧成功水位，重新建立范围内索引；仅通知选项变化不清游标。实际服务 ID 在原地址更换时也执行同样保护。

每批事务复用已经核验的配置、当前媒体和批量读取的来源、根、账号、状态、证据及成员资料。缓存只存活于这次事务，不能用准备期结果替代提交期身份核验；SQLite 可在同一个写事务内复用已经核验的相同范围。PostgreSQL 普通独立组使用共享索引保护与按稳定顺序取得的带媒体类型的条目 ID 事务锁；发现旧成员关系时先回滚，再以排他保护重开事务。配置变更、删除和复杂组保留排他屏障。SQLite 继续单连接写入，用 `UPDATE … RETURNING` 一并取得写保护和状态。

PostgreSQL 删除同步目录和批量写入文件账本时，必须在修改任何来源记录前取得同一索引排他保护，避免它们与快照事务按相反顺序锁定文件、目录及旁车。仅更新账本时间的批次也遵循此顺序；这项协调不推进索引版本，SQLite 保持原有写事务。

媒体、文件关联、状态和成员投影仅在内容变化时写入；媒体更新只写实际变化的列，已有媒体库／同步根关系先检查存在性。证据相同仍维护全量标记、最后观察时间和原始播放 URL，并修复缺失或含 SQL NULL 的派生记录。批提交在事务内预读 membership，完全一致时跳过写入；需要写入时仍使用条件 UPSERT，NULL 不能当作等价零值漏修。

SQLite 构建 membership 时可复用本次已构造的 evidence 条目，无法保证与 JSON 解码等价时沿用持久 JSON 路径；PostgreSQL 使用 JSON 路径。两库都完整持久保存 evidence JSON，复用只减少内存中的重复解析，不改变证据格式和删除授权。SQLite 的直接条目、分段和版本成员分别逐 ID 等值读取，合并后保持原排序；直接条目 ID 保持全局语义，分段和版本成员按服务器限定。

索引全量清旧只移除当前媒体项／关联，保留不可变物理证据。冻结证据包括已有 SyncFile 的来源、账号主体、同步根、file_id 与独立哈希／mtime，以及当时已知的旁车身份；缺字段和路径冲突保留原因，不能升级为删除授权。旧 ServerId 为空的历史行需要成功同步补全，不能自动认定属于当前服务器。主项完整响应解除旧成员关系时沿用旧文件证据，不重新绑定当前账本的同路径新文件；仍带删除屏障的消失成员只解除当前索引中的成员关系，不修改屏障、冻结证据和未完成删除工作。同步范围摘要仅用于索引提交，删除必须核对独立服务连接身份；选库变化不构成删除白名单。结构与保留约束见 [数据库 schema](../reference/database-schema.md#emby_index_statesemby_item_statesemby_item_evidences)。

### 手动全量同步

手动同步用于低频校验或重建本地索引，同样要求本端 `enabled=true` 与 `sync_enabled=1`。总开关关闭仍可只读查询媒体库以准备配置。

`POST /api/{emby|jellyfin}/sync/start` 接受任务后返回 HTTP `202`，`data={status:"submitted", media_server_type:"emby"|"jellyfin"}` 表示本端条目同步已受理；最终结果从状态接口读取。未配置返回 `404`、`MEDIA_LIBRARY_NOT_CONFIGURED`；连接或同步设置未就绪返回 `409`、`MEDIA_LIBRARY_SYNC_UNAVAILABLE`；本端已有任务运行返回 `409`、`MEDIA_LIBRARY_SYNC_RUNNING`。外层字段遵循 [API 响应与请求错误](../reference/api-response.md)。

媒体库列表的连接未配置完整时返回 `409`、`MEDIA_LIBRARY_CONNECTION_UNAVAILABLE`；直接桥接媒体服务器失败按实际原因返回 `502` 或超时 `504`。列表已成功更新但本地清理失败时，读取成功结果和顶层 `warnings`，不能将其作为未更新重试。

流程：

1. 生成本轮 `sync_run_id`。
2. 按媒体库分页拉取 Emby item。
3. 每个 item upsert 时写入 `last_seen_sync_run` 和 `last_seen_at`。
4. 某个媒体库完整同步成功后，只清理该媒体库内 `last_seen_sync_run != 当前批次` 的旧条目。
5. 全部媒体库成功后，更新全量成功时间，并以本轮扫描开始时间单调推进增量游标；已有更大的游标保持不变。
6. 某个媒体库分页、分段补查、关联或保存失败，该库不清旧；成功库可独立完成，但本轮不会推进全量成功时间或增量游标。非末页空响应、变化的总数、重复 ID 或条目数矛盾均算失败。

全量同步不再维护巨大的有效 item ID 列表，也不再对每个 item 固定 sleep。

配置所选媒体库在本轮库列表中全部或部分缺失，或过滤后没有实际发起扫描时，本次全量不推进增量游标；保留原有筛选和返回行为。实际扫描已选媒体库得到完整空结果仍可推进，不能把未扫描与成功空扫描混为一谈。

### 定时同步

两端各有独立固定 Cron EntryID。只有本端 `enabled` 和 `sync_enabled` 均启用时登记任务；默认表达式为 `0 * * * *`，含义是每小时整点执行一次。普通保存只替换本端媒体 Cron，不重建同步、预加载、备份等其他任务；全局初始化或恢复后重新登记两端。

当 `enable_daily_first_full_sync=1` 时，每天第一次定时同步会执行全量同步；判断依据是 `last_full_sync_at` 是否属于服务器本地时区的当天。全量同步成功后会更新 `last_full_sync_at`，当天后续定时同步执行增量同步。如果当天首次全量失败，`last_full_sync_at` 不会推进，下一次定时同步仍会继续尝试全量。

当 `enable_daily_first_full_sync=0` 时，Cron 每次都执行增量同步。

保存本端配置时，如果兼容客户端没有提交 `enable_daily_first_full_sync` 字段，后端会保留当前已有配置；只有显式提交 `0` 或 `1` 时才会修改该开关。

### 定时增量同步

请求使用 Emby `/Items` 的 `MinDateLastSaved` 参数。OpenAPI 中该参数类型为 `string`、格式为 `date-time`，分页参数为 `StartIndex` 和 `Limit`：

```http
GET /emby/Items
?ParentId=<libraryId>
&Recursive=true
&IncludeItemTypes=Movie,Video,Episode
&Fields=DateCreated,DateModified,ParentId,PremiereDate,Path,MediaSources,PartCount,SeriesId,SeasonId,SeriesName,SeasonName,IndexNumber,ParentIndexNumber
&MinDateLastSaved=<cursor_minus_overlap_rfc3339>
&SortBy=DateLastSaved
&SortOrder=Descending
&StartIndex=0
&Limit=100
```

响应示例：

```json
{
  "TotalRecordCount": 1,
  "Items": [
    {
      "Id": "10001",
      "Name": "示例影片",
      "Type": "Movie",
      "DateCreated": "2026-06-01T12:00:00.0000000Z",
      "DateModified": "2026-06-20T08:30:00.0000000Z",
      "HasPath": true,
      "MediaSources": [
        {
          "Id": "mediasource_10001",
          "HasPath": true,
          "PathPrefix": "http://qmediasync:12333/"
        }
      ]
    }
  ]
}
```

游标规则：

- 本轮开始时记录 `scan_started_at = now.UTC().Unix()`。
- 查询时使用 `last_saved_cursor_at - 600 秒`，初始或小于 overlap 时使用 Unix 0。
- 本轮内用 item ID 去重。
- 全部媒体库成功后更新 `last_incremental_sync_at`、`last_processed_count` 和 `last_sync_time`，并以扫描开始时间单调推进 `last_saved_cursor_at`；全量成功也推进同一游标，后续增量仍保留 600 秒重叠窗口。
- 任一媒体库失败时不推进 `last_saved_cursor_at`。
- 不依赖响应中的 `DateLastSaved` 推进游标，因为实际响应不返回该字段。
- 增量同步不做全局删除。

过滤边界：

- `MinDateLastSaved=2999-01-01T00:00:00Z` 这类未来时间应返回空集合。
- 空集合只表示本轮没有变更，不代表本地已有数据应被删除。
- 因响应不返回 `DateLastSaved`，不能用最后一条 item 的时间推进游标。

### Webhook 单条同步

Webhook 新增或修改事件只按 item ID 查询单条并 upsert：

```http
GET /emby/Items?Ids=<itemId>&Fields=DateCreated,DateModified,Path,MediaSources,PartCount,ParentId,SeriesId,SeasonId,SeriesName,SeasonName,IndexNumber,ParentIndexNumber
```

响应示例：

```json
{
  "TotalRecordCount": 1,
  "Items": [
    {
      "Id": "10001",
      "Name": "示例影片",
      "Type": "Movie",
      "DateCreated": "2026-06-01T12:00:00.0000000Z",
      "DateModified": "2026-06-20T08:30:00.0000000Z",
      "HasPath": true,
      "MediaSourceCount": 1
    }
  ]
}
```

如果需要用户态字段，可以改用：

```http
GET /emby/Users/{UserId}/Items/{itemId}?Fields=DateCreated,DateModified,Path,MediaSources
```

兼容注意：

- `/Items/{itemId}` 在部分 Emby 服务上可能返回 `404`，不能作为唯一单条详情路径。
- `/Items?Ids=<itemId>` 更适合无用户上下文的单条查询。
- `/Users/{UserId}/Items/{itemId}` 适合需要用户态字段时使用。

规则：

- 返回单条 Movie、Video 或 Episode 时，连同已确认的版本／分段物理快照写入本地 `emby_media_items`；其他类型不会补物理详情或入库。
- 写入前会通过 `/Items/{itemId}/Ancestors` 和 `/Library/VirtualFolders` 解析真实所属媒体库，不能把 Episode 的 `ParentId` 当作媒体库 ID。
- 当 `sync_all_libraries=0` 时，解析出的媒体库 ID 不在 `selected_libraries` 中会跳过本次单条同步。
- 解析到 PickCode 时建立 `emby_media_sync_files` 关联。
- 空结果或不支持的类型只记录日志，不触发全量同步。
- Webhook 单条同步沿用本次核验的配置快照与父收件原 ServerID；地址或同地址实例变化都不能转投新服务器。它不推进 `last_saved_cursor_at`。
- 同步忙时返回可识别的 `ErrEmbySyncBusy`；该结果与远端不存在不同，不声称条目已处理。

### Webhook 通知配置

在 QMediaSync 的 Emby 设置页保存服务器地址和 Emby API Key，启用条目同步，完成一次全量 Emby 条目同步，再配置通知。升级后也应先成功完成一次全量同步，补齐版本、分段和文件身份；它只能补全仍可查询的条目，不能恢复已消失且从未保存的历史身份。

1. 在 Emby 通知设置中新建 Webhook，填写 QMediaSync 设置页显示的“Emby 通知链接”。启用“通知链接鉴权”时，使用 QMediaSync API Key，通过 `X-API-Key` 请求头或链接的 `api_key` 查询参数传入；这里使用的不是 Emby API Key。
2. 内容类型选择 **JSON（`application/json`）**，关闭分组（`GroupItems`）。不使用把 JSON 放在 `data` 字段中的 `multipart/form-data` 格式。关闭分组仍可能有 Emby 自身的通知缓冲，不保证即时投递。
3. 按需要选择发送通知的媒体库，勾选“已添加新媒体”（`library.new`）和“媒体已移除”（`library.deleted`）。界面按库名选择；直接配置 Emby 通知 API 时，`LibraryIds` 使用库 Guid，不能填 QMediaSync 索引中的数字 item ID。QMediaSync 的同步选库只约束条目同步，不是独立的删除白名单。
4. 如事件列表提供独立的移动、重命名、扫描失效或移除媒体库事件，不勾选它们用于联动删除。普通 `library.deleted` 也可能由重命名或扫描发现文件消失触发，不能仅靠取消独立事件排除误触发；QMediaSync 仍会核验文件身份、原条目／STRM 及存活使用者。
5. 确认通知所属用户和实际操作用户。通知所属用户与“用户事件过滤”是不同设置，管理员名下的通知不代表已覆盖其他用户的增强事件。用可丢弃的测试媒体验证实际操作能向 QMediaSync 投递所选事件；验证投递时保持联动删除关闭，避免涉及网盘原片。

官方通知可独立使用，无需安装插件。使用神医助手或 MediaInfoKeeper 时，推荐只开启插件的**通知增强**，并在 Emby Webhook 中额外勾选“媒体深度删除”（`deep.delete`）；无需开启插件的物理深度删除。QMediaSync 按受支持的事件和字段结构内置识别，不要求选择插件品牌或增加插件开关，也不会修改 Emby／插件配置。其他增强事件和分组描述不用于推断待删成员。增强通知只补充证据，即使收到 `deep.delete`，也不能认定原 STRM 已删除成功。

需要联动删除网盘文件时，再在 QMediaSync 中开启“删除时联动删除网盘文件”。官方与受支持增强通知共用此开关：接收成功只表示事件已保存，后台核验后才处理确定文件。条目或原 STRM 仍存在、来源共享、身份未知或查询失败时保留文件，未完成原因见服务日志。关闭期间收到的通知，以后启用也不追溯补删；执行和重试前仍检查开关及目标身份。

具体范围见下文[目录清理策略](#已采纳的目录清理策略)：Movie、Season、Series 已有可信媒体目录身份且没有明确保留成员时，可以整目录清理，包含陌生文件和未关联视频；证据或来源能力不足时退回明确文件。Episode 仍仅处理 part1 和明确专属旁车，Video 仅自身；保留的版本、分段、其他季、共享使用者及同步根受到保护。网盘删除后的本地 STRM 和 SyncFile 记录由后续符合条件的完整 STRM 对账收敛，不自动触发即时清理；完整对账资格见 [STRM 同步调度](sync-orchestration.md)。

### Jellyfin 官方插件事件

`POST /jellyfin/webhook` 使用本端总开关、连接及 Webhook 认证，接收官方插件 v21／v22 的 Send All Properties 标准 JSON。正式配置使用 Generic Destination、`Content-Type: application/json` 和 QMediaSync 的 `X-API-Key`；内部解析可兼容合法 JSON 的 `text/plain`，身份和大小限制不放宽，详见 [入站边界](../engineering/request-validation.md#jellyfin-webhook-入站边界)。

| 官方 `NotificationType` | 内部事件 | 处理 |
| --- | --- | --- |
| `ItemAdded` | `library.new` | 本端读取真实详情，维护索引；按分项自动提取、发送新增通知 |
| `ItemDeleted` | `library.deleted` | 固定接收时授权，使用本端历史证据构建删除工作 |
| `PlaybackStart` | `playback.start` | 本端播放开始通知 |
| `PlaybackStop` | `playback.stop` | 本端播放停止通知 |

插件正文没有原始 `Path`／`ParentId`，不能伪造路径、合成 `ItemUpdated` 或 `deep.delete`；没有历史证据的移除不能提供网盘删除资格。UUID 支持只解决条目定位，真实 ServerID、原条目消失、STRM 与账号／文件身份及存活使用者核验仍须完成。两端新增缓冲、播放去重、详情与图片缓存分别隔离；渠道仍共用 `media_added`、`media_removed`、`playback_*` 等原机器值，正文标明产品。关闭本端 `enable_media_notification` 只停止发送，不取消已授权的业务和清理。

媒体通知由 `StartMediaLibraryNotifications()` 启动两端本地聚合，不等待远端；`StopMediaLibraryNotifications(ctx)` 停止入队、取消并等待事件处理与发送，超时且旧工作未退出时不能重启。新增媒体先独立入队自动提取，再发送通知，慢／失败通知不阻挡提取；关闭发送分项不停止同步、提取或删除。删除消息优先使用本次收件冻结的本端名称／剧名，不借另一端或当前新索引改写历史展示。

两端 Webhook 工作日志采用 `名称（ItemId ...）`：整季显示 `剧名 S01`，单集显示 `剧名 S01E06`，特殊季保留 `S00`。已有通知中的有效名称和编号直接使用；字段缺失时，只从本次收件冻结的本端删除输入补足对应主 Episode 的资料，整季按匹配的 SeasonId 汇总一致剧名和季号。隐藏分段默认零值不替代主集资料；不足或冲突时保留可靠的现成名称或条目 ID，不猜编号、不查询当前索引或远端。

工作结果明确区分“条目同步已完成”和“删除处理已完成”，等待、重试及停止重试也保留对应动作。删除处理完成表示本次通知工作结束，实际云端对象是否删除以逐目标结果为准；联动删除关闭、跳过或原对象已不存在时不得写成新发送了网盘删除。名称格式只影响展示，不改变已冻结授权、删除范围或机器状态。

### 入库通知时间

电影入库通知使用本端媒体详情的 `DateCreated`。电视剧合并通知按本批新增单集 ID 批量查询 `DateCreated`，取本批单集添加时间的最大值，不使用整部剧的创建时间。缺失、零值、解析失败或查询失败的单集时间，依次回退到该条 `library.new` 的 `Date` 和 QMediaSync 接收该事件的时间；电影使用相同的回退顺序。等待合并与发送通知不会改变这个时间。

时间统一转换为程序本地时区（北京时间，UTC+8），以 `YYYY-MM-DD HH:mm:ss` 显示，支持两端返回的 RFC3339 小数秒和时区偏移。单集查询只包含当前批次，每批最多 100 个 ID，整个批量查询最多等待 30 秒；未查到的单集继续使用各自的回退时间。

### Webhook 持久接收与后台处理

收件共享原存储与管理器，按固定 Emby／Jellyfin 分支有界执行。同端保留原优先级和串行顺序，慢端不阻塞另一端。启动先恢复遗留工作再开放处理，关闭等待全部分支退出，旧执行者未退出前不能启动第二轮管理器。关闭总开关保留待处理工作并排除本端调度，重新启用时唤醒；不通过忙轮询或耗尽网络重试结束关闭期间任务。远端删除仍通过共享物理来源锁和数据库维护边界。

`POST /emby/webhook` 保留现有鉴权、`X-API-Key` 与旧 `api_key` 查询参数兼容。官方教程使用 `application/json`。请求先校验体积、JSON 类型与关键字段，不记录原始正文或带凭据的播放 URL；关键字段冲突不生成删除工作。保存失败返回非成功响应，成功仍返回兼容的响应形状，仅表示事件已保存。

内置处理 `library.new`、兼容的 `library.modified`、`library.deleted` 及受支持的 `deep.delete` 结构，不需要选择插件品牌。服务器版本、Title 或是否带 User 都不能可靠识别插件。其他通知保留原有功能；分组通知的描述文本不被猜测为子条目列表。

接收事务保存必要字段、服务器连接身份、接收时的删除授权及冻结输入，并原子登记删除屏障。每次通知独立保存，不按 ItemId 或事件 Date 永久去重。官方与增强通知通过同一物理文件代际的结果避免重复删除；后到通知仍可处理已由历史证据确认的范围。同步选库只约束索引同步，不作为删除白名单。

应用启动后运行共享管理器的两个固定后台分支，工作不绑定 Webhook HTTP 请求的取消。停止必须等旧分支全部退出后才允许新一轮启动；普通备份使用数据库快照，不暂停处理。新增／修改事件先尝试读取详情并保存早期不可变证据，即使全量同步正忙也不绕过锁写当前索引；后续仍通过普通同步入口更新索引。读取前同时记录已有证据水位，读取期间同条目的新快照会使旧观察失效；不同条目的更新不会互相废弃已保存证据。删除接收只在该条目的原状态未变化时采用这份证据。若官方缓冲通知到达时条目早已删除、此前也没有可靠身份，仅凭当前 Path 唯一命中不能补造旧文件身份，保留未完成原因。

删除收件采用早期观察时，已有且匹配原状态的索引必须在同一事务内更新快照／代际，并按观察中冻结的文件重建关联，避免把自身旧索引误判为其他使用者；不能给旧文件关联直接换上新快照，也不能从当前账本补造身份。未建索引的条目仍不新增索引，展示字段、全量批次标记和同步水位仍由普通同步维护。任一步失败，身份更新与删除收件一起回滚；真实共享文件仍受删除前核验保护。

同一条目有多份早期观察时，先排除预期状态不匹配的候选，再按不可变证据 ID 选择最新一次成功保存的观察，最后判断是否属于删除范围。收件顺序和秒级时间戳不代表成功读取顺序；旧通知重试取得的新证据可以更新选择。最新有效观察明确属于另一个季／剧或分段主项时，在本次冻结候选之前排除该条目，不回退到旧观察或旧状态中的成员关系；它不进入本次删除目标，也不登记删除屏障。排除仅影响本次收件，不更新该条目的当前状态；未知归属、无效观察不能作为移出证明。直接删除该 Episode／Video 时仍按自身 ID 处理。

同步忙时保持待办，不消耗失败次数。网络处理有界重试，失败上限为 4 次；每个删除目标保存自己的结果，已成功目标不重复发送删除。保存结果暂时失败时先重试持久化，不重发刚完成的网盘请求；应用取消时保留领取状态，启动恢复后先核验原身份。未知、冲突或超出重试范围的工作保留原因，不自动换成当前路径的新文件。工作状态保存在数据库并通过现有日志报告，不计入 EmbySyncMode，也没有新增任务页面。

115 返回 `990019` 表示上一项删除尚未完成，目标结果保留明确原因，沿用现有延迟重试及重试前身份核验，不增加固定冷却或接口内部重试。删除接口成功、详情已不存在不代表 115 后台删除操作已经结束。删除专用详情查询确认 `430004`／`231011` 缺失时，队列日志显示“确认目标已不存在”；普通查询和不明确的响应保留原日志。

剧集删除通知的入缓冲、等待合并、达到触发时间，以及缓冲区大小检查和清空停止轮询这五类日志使用 DEBUG；通知发送和联动删除流程不变。

删除失败时，应用日志以 WARN 记录 `Emby 删除诊断`，包含通知编号、处理轮次、来源、账号、原文件／父目录 ID 和该目标累计发送次数；核验阶段失败可能尚未发送，发送次数可为 0。115 删除入口以 ERROR 记录 `115 删除诊断`，包含账号、文件／父目录 ID、HTTP 状态、响应可解析标记、`state`／`code`／`errno`、固定错误类别及耗时。耗时包含客户端排队和既有重试等待，不等同于纯 HTTP 耗时；HTTP 为 0 表示未取得可用状态，响应不可解析时不能把默认 `state=false`、错误码 0 当作上游返回值。两份日志通过时间、账号和对象 ID 关联，不新增请求或改变重试策略。诊断不输出原始上游消息、响应正文、请求头、Token、Cookie 或带签名 URL；成功请求不产生失败诊断，播放清理的已明确删除结果沿用原有静默规则。

同一执行批次内的视频与专属旁车共同接受本轮核验，不能仅因上一轮视频待核验就提前排除同批旁车。跨批时，组外相关视频只有已确认删除或缺失才解除附件依赖；尚未产生结果、待核验和发送失败等未完成状态都阻挡附件。相关视频本轮尚待后续批次处理时，先暂缓附件，否则保留附件；原批次处理完成后，只有相关视频均已确认删除或缺失，才汇总这些附件，按来源、账号、真实父目录和现有文件数量／请求体字节限制重新分批核验、删除。本轮仍有共享、身份冲突、发送失败或次数耗尽等未完成结果时，暂缓的附件继续保留。

暂缓仅使用本轮内存，不增加发送次数上限，也不重新开启已终结的历史通知。补处理附件沿用批量删除和结果保存流程，可能增加必要的核验、删除批次及数据库交互，不能保证跨批执行和异常重试的总请求数不变。

接收时未获删除授权的事件，以后开启开关也不会自动补删；执行和重试仍检查现有 `SyncEnabled`、`EnableDeleteNetdisk`、服务连接及账号／文件身份。此类事件只允许在核验服务连接、原条目 ID 已消失后，按冻结快照与代际清理本地索引，不要求存在可删除的网盘来源。已确认新 ID 仍使用同一来源的重命名场景，也只清理消失的旧关联，保留共享网盘文件与新关联；其他未知或执行失败的范围继续保留。数据库恢复进入维护后停止接收并等待已有收件事务和 worker 退出，保持维护直到重启，期间 Webhook 返回暂时不可用；普通备份通过一致读快照保留持久收件与证据。恢复过程见 [数据库运维](../operations/database.md)。

`deep.delete` 只提供额外证据，不代表原删除成功。JSON `Item.Path` 保持完整文件路径，包括合法文件名中的换行；Description 中的 Item Path 可能只是目录，不授权递归删除。单一、完整的 Mount Paths 候选只能与已有历史来源核对，多行文本无法可靠区分多文件和文件名换行，不按换行或逗号拆成删除目标。没有独立历史映射的候选保留原因，明确身份冲突停止执行。

Webhook 删除事件不触发全量同步，也不调用刷新媒体库接口。删除前重新核验真实服务器、原条目 ID、原 STRM 路径及可访问的同步根；再枚举不受同步选库限制的完整物理清单、来源和 AdditionalParts，排除重命名、新 ID 和共享源。条目／STRM 仍存在、清单不完整或查询失败均不授权网盘删除；失败的深度删除通知不会清掉仍存活的正确索引。确认原条目存活时仅释放匹配的临时屏障，旧查询依然无权提交。

Jellyfin 删除主项后，用户态详情可能继续返回已失去主项的附加 Video。仅当本次冻结的 `PartOfItemID` 明确指向同一删除输入内的主 Movie／Episode、该主项已不存在、详情仍为同一路径的 Video、完整当前清单没有重新认领或共享该来源、且受管原 STRM 经原根与路径核验明确不存在时，才兼容这种附加分段残留。单独的管理列表漏项或本地文件缺失都不足以放行；普通版本、其他存活条目、路径变更及读取失败仍沿用既有保护。该处理不修改 Jellyfin 数据库，也不提升旧通知的冻结授权。

若先前删除因查询故障结束，后续同步和新的 Webhook 都能重新核验仍存活的主项及分段。全量、增量同步按每页 100 条核验已有屏障；单条同步仅严格读取目标及实际确认的版本／AdditionalParts，不遍历无关删除历史。隐藏分段可用该条目历史主项关系作为查询入口，但实际响应必须确认目标仍属于该组，不能凭历史关系恢复成员。解除屏障后，整组旧响应作废，重新取版本和读取；没有解除屏障时复用本轮读取。单条同步最多在本次调用内重新读取一次，之后的并发冲突交给既有重试；增量本轮需要恢复时从 Unix 0 查询现存条目，仍不进行全量清旧。此过程只恢复索引，不重启旧删除或提升旧事件授权。

Jellyfin 隐藏 Video 即使可按自身 ID 读取，也可能没有祖先；单条同步先经历史主项入口核验当前 AdditionalParts 成员关系，以实际主项解析所属库，不把空祖先当作任意选库的依据。Series／Season／Folder 新增不建立物理文件索引，使用 `DEBUG` 明确记录跳过，不能误报“未找到条目”或当作已同步文件；相应删除事件仍按原范围处理。恢复入口和目录角色的条目 ID 校验统一支持已有十进制 Emby ID 与规范化 Jellyfin GUID。

### 精确文件联动删除

Emby 与 Jellyfin 的删除保护均限于本端：另一端索引、成员、历史目标或共享引用不参与查询和授权。两端引用同一物理网盘文件时，用户需自行安排删除；共用物理来源锁只协调同时执行，不产生跨端引用保护。新设置与凭据不能扩大已冻结通知的原身份或授权。

联动删除分为接收事务冻结、构建计划、执行和条件收尾四个步骤。接收事务读取不可变条目证据，保留当时的关联、来源／账号主体、同步根、物理文件代际及清理政策；当前索引已被完整扫描清理时，仍可使用保留下来的 state→evidence。同目录视频账本在接收时冻结；独立删除旁车必须已有正常同步或早期观察保存的历史身份。接收时的当前 SyncFile 不能替代这份历史证明，旧证据缺少旁车身份时保留元数据；重试不会选择同路径后来出现的文件。以下是文件级成员范围，目录权限另外按下一节核验。

早期观察候选和证据冻结共用持久成员索引，先按目标、真实季／剧或分段父项确定候选，再加载相关完整证据；不因无关媒体或删除历史增长而逐条读取其 JSON。成员索引跟随状态引用的历史证据，与状态更新同事务保存；当前展示索引被清理、带屏障成员只从当前展示关系中移除时，历史成员关系仍保留。成员索引只帮助定位，删除范围与授权仍核对原始证据、当前状态及本次移出排除集合。修复和备份恢复从原始状态与证据重建，不信任归档中的派生行。

| 删除类型 | 文件范围 |
| --- | --- |
| Movie | 主项及通过 AdditionalParts 确认属于它的分段；不扩展到保留的独立版本。 |
| Episode | 主项 part1 及其明确专属旁车；保留其他 part，允许后续重新入库。 |
| Video | 该物理条目本身。 |
| Season／Series | 按保存的真实季／剧成员 ID 收集文件和确认分段，覆盖所有关联目录和账号；不根据目录名称推断范围。 |

文件批量模式只删除已授权的明确文件。旁车先按共享名排除和明确 NFO／字幕／图片后缀取得宽松候选：字幕是点边界前缀，不限定语言标签（含中文多标签）。归属取最长视频 stem，精确同名优先于较短前缀，同 stem 不同容器并列保留；任一归属使用者被保留或身份未知即整体保留。判定同时考虑历史视频证据和执行前完整新鲜目录，并允许冻结证据记录前缀候选超集，删除权限始终由计划／执行期归属复核把关。通用 `poster.jpg`、`folder.jpg`、`tvshow.nfo` 不因同目录关系获得独立文件权限；季海报需要单独的历史季归属。已授权视频与专属旁车一起提交，按实际结果分别确认。目录整删包含的未知内容不需要伪造文件归属。

一轮领取执行共用一次现有 `syncscope` 全局保护；不在 SQL 事务中等待或执行 HTTP，也不嵌套获取范围。执行层要求独立服务器、原条目／STRM 和存活使用者核验；缺少核验不调用网盘。文件身份与授权在远端只读核验后、单次破坏性请求前再次检查。115 使用准确的对象 ID 和真实父目录 ID，百度使用完整路径，OpenList 使用目录和 basename；删除写请求不会在客户端内部自动重放。

网盘同步根遵循[同步目录路径约定](../reference/sync-path-api.md#sync_path)，保存时移除前导 `/`；115 的文件账本通常也不带 `/`，百度和 OpenList 的文件路径则可能带 `/`。保存删除身份和执行删除时，三个来源均将合法的根相对目录与对应绝对表示按同一网盘目录比较，范围和同步根保护使用相同规则；本地 STRM 路径仍须为绝对路径。路径含向上跳转、非法分隔符或无法确认归属时拒绝删除。路径表示相等不能替代账号、文件 ID、父目录 ID、大小、哈希及时间等身份核验，也不会改写已保存的历史证据、清除历史失败原因或重新执行终态 `unresolved` 事件。

每个目标分别返回 `deleted`、`already_absent`、`unresolved` 或 `failed`。错误、false、取消、未知结果、不支持的来源和身份冲突均保留未完成证据；不能将查询失败视作不存在。收尾仅删除全部目标已完成、且仍为原快照代际的 owner 关联，不按 `sync_file_id` 清除其他使用者。某目录旁车清单不可用、身份变化或历史身份未确认时，按来源、账号和目录匹配，只保留关联 owner，其他目录已完成 owner 可以独立收尾；无法定位影响范围的未知计划问题仍阻止收尾。不可变证据保留；`SyncFile` 和本地派生文件仍由后续符合条件的完整 STRM 对账收敛。

官方／增强事件由持久 worker 接入上述计划 API。标量 `DeleteNetdisk*By*Id` 旧入口无法提供独立核验，继续返回待核验错误并保留本地索引。`syncscope` 只协调本进程内遵守该协议的操作，不能消除外部系统在最后核验与删除之间的写入窗口。

### 已采纳的目录清理策略

新收件冻结版本 2 清理政策，优先完整清理有可信归属的媒体目录；不满足目录条件时，将选定视频与专属附件合批。启用目录能力需要先完成相应 STRM 账本和 Emby 条目同步，建立删除前证据；升级不会使旧通知自动获得新范围。

同一轮持有范围保护的执行复用完整 Emby 存活核验，包括分页和 AdditionalParts。完整采集有独立的 5 分钟上限，成功完成后最多复用 30 秒；扫描本身不是原子快照，早页可能早于完成时间。每批仍检查当前授权、账号、代际、共享关联和相关条目；超时、重领、释放范围或相关版本／配置变化后重新核验。完整网盘目录清单提供足够身份字段时，不再逐文件重复读取详情。

| 删除操作 | 处理范围 |
| --- | --- |
| Movie 最后版本或版本独占目录 | 有删除前作品／版本目录归属证据、没有明确需要保留的成员时，整目录清理，包含陌生视频、共享图片、NFO、TXT 和附件。其他版本仍在共用目录时，批量删除选定视频及明确专属旁车，保留其他版本与共享内容。 |
| Episode／独立 Video | 保持 Episode part1／Video 自身及明确专属旁车的范围，不自动提升为整个季／剧目录删除。 |
| Season | 确认整季删除且没有明确需要保留的成员时，整删有可信归属的季目录，陌生文件包括未关联视频随删；另清理已保存历史身份的剧根本季海报。存在其他季或共享成员的混放目录退回明确文件，保留剧根及剧级共享文件。 |
| Series | 确认整剧删除且没有明确需要保留的成员时，直接删除最高可信剧目录，陌生文件包括未关联视频随删；子文件／子目录不另发删除请求，不继续上溯分类目录。 |

目录必须在删除前建立真实对象身份与媒体归属，不能以目录名或“没有其他 Emby 关联”反推归属。Movie／Season／Series 统一以可信目录范围授权，只有明确需要保留的版本、其他季／作品或共享使用者才构成成员阻挡；陌生归属本身不阻挡。所有同步根及祖先、嵌套同步根仍独立保护，Episode／Video 不自动获得父级目录权限。

“最高合法剧根”从已有正向证据的候选中选择：正常同步／早期观察保存 Series／Season／Movie 的真实路径和祖先角色，经 SyncPath 映射并核对网盘目录 ID 与父链。Movie 使用条目真实父目录证据（Ancestors 中 ID 等于条目 ParentId、Path 等于条目文件所在目录的父文件夹），或前述 Jellyfin 受管电影目录证据；QMediaSync 刮削已完成重命名的明确输出目录也保留为回退来源。目录名或仅知道外部电影的文件路径不足以启用整删。验证当前事件范围、原目录身份、保留成员和根保护后，选择能够覆盖子操作的最高媒体目录，不逐级向分类目录试删。Season 只到季边界，Series 可用剧根覆盖全部季；跨账号／真实根分别处理，不取共同分类祖先。

百度的刮削输出回退证据还要求历史 `Media.VideoPickCode` 中的 fsid 非空，并与本次视频的 fsid 一致；路径和文件名相同不足以证明仍是原文件。缺失或不匹配时仅弃用这份刮削证据，独立有效的 Emby 真实父目录证据仍可参与核验。

排他检查即检查目录内是否有明确需要保留的成员，采用账本交叉检查、持久删除结果与本轮完整 Emby 存活核验的组合，不以纯账本替代存活核验。查询限定来源、账号和真实目录子树，以少量本地集合查询检查 `sync_files` 与媒体关联，排除已完成同代际删除的旧关联；复用本轮 Emby 存活核验与 AdditionalParts，保护未入本地账本的已知使用者。相关信息在有效窗口内跨批复用，避免重复全库扫描及重复读取；完整核验仍按实际 HTTP 请求计数，过期或相关变化后重新取得。必要查询失败不能当作空集，不逐个查询陌生文件的归属，也不承诺固定 SQL 次数。目录身份、父链、挂载边界及保留成员位置可独立确认时，无需仅为识别陌生内容而递归列举整树；仍缺必要边界证据时补列表／详情，或退回明确文件。

整删前读取待删目录的一层完整清单，与本轮 Emby 存活来源及同来源、同账号的账本身份核对；即使账本还记着目录外的旧位置，清单中出现仍在使用的原文件，也须保留目录并退回明确文件。115 按文件 ID／pickcode，百度按 fsid 核对，不能拿百度账本的路径型 FileID 与远端 fsid 比较。清单只读取直接子项，不递归进入普通子目录，不逐个查询陌生视频、NFO、图片、字幕或 TXT 的详情及内容。单页、无重试且没有可复用清单时，每个待删目录增加一次列表请求；分页与重试另计，清单失败不能当作空目录。

这是一层额外保护，不逐一反查全库已命中账本的存活文件。用户在网盘外部移动文件、尚未同步更新账本，且文件被移入待删目录的更深子目录时，仍可能随整目录删除；此边界用于保留整删能力并控制请求量。同步根、已知保留成员和原目录身份等既有保护继续生效。

发现存活 Emby 条目的网盘来源时，先核对一层清单并复用已有账本定位；清单和账本无法定位才尝试只读反查。当前仅支持与待删目录同来源、同账号，且播放地址匹配已配置 QMediaSync STRM 基础地址与受支持路由的 115／百度来源；地址必须明确携带与当前账号主体一致的 `userid` 和对象标识。115 用 pickcode 取得文件 ID，再核验详情与真实父链；百度按 fsid 查询当前真实路径。反查只访问现有网盘客户端，不请求播放地址或下载影片，不凭本地 STRM 目录、URL 中的路径参数或陌生文件名推断真实位置。来源在目录内、账号或地址归属不明确、返回身份不符及查询失败都保留目录并退回明确文件；确认在目录外只解除这一处阻挡，其他目录授权与保护仍须通过。

反查仅针对完整 Emby 清单中仍被使用、且位置未知的视频来源，包括已确认分段和版本；不逐个查询目录里的陌生视频、NFO、字幕、图片或 TXT。相同来源的结果在本轮执行内去重复用，失败也避免跨目录反复请求；成功结果受原读取时间及现有 30 秒核验窗口限制，命中不续期，并复核账号与地址配置。超时、释放范围或重领后不能继续使用旧结果。反查增加的读取随不同未知来源和所需接口调用增长；成功整删可能省去文件级列表／确认请求，总请求数取决于实际目录和文件规模。

反查在删除准备阶段完成。整目录删除进入供应商队列的最终发送检查后，只消费已经完成且仍有效的核验结果；清单或来源结果缺失、仍在读取或已过期时直接拒绝发送，不在队列回调内重新扫描全库或排入网盘反查。原条目／STRM、账号、配置和授权检查仍执行；取消与反查时限传递到实际 HTTP 请求，避免退出后残留读取。

文件批量路径将同来源、账号与真实父目录内的选定视频及已确认专属旁车共同核验、冻结并提交，旁车不能有保留使用者。明确的成员身份冲突或存活使用者只阻止相关成员及其依赖旁车，其余独立授权成员继续合批；全局授权、领取或必要查询失败仍停止执行。不超出本地 100 项／16 KiB 编码体积预算的一组以一次删除写请求为目标，这不是供应商公布的最大值；跨目录／账号或超限时分包。混放目录中的陌生文件不因此获得文件级授权。视频与专属旁车共同提交，接受非原子批处理出现视频未删而旁车已删，按原身份保存并恢复各目标结果，已完成成员不重删。一次提交不等于全程只有一次 HTTP，也不表示整体响应证明每个文件独立删除；false、缺项、超时或断线均不能当作整批未执行后直接重发。

同一范围内，计划、批次执行和 provider 复用尚未过期的完整目录清单；来源、账号、真实父目录、位置版本或适用的写入版本变化后重新读取，任何已尝试写入都会使相关清单失效。已知同步根需要按真实位置保护，不能只看可能过时的配置路径；已有父链可复用，其他根需必要的原 ID 定位。无法确认位置时退回文件模式，不为陌生文件逐项查归属。

同一轮计划／核验可按 owner 复用已解析的历史文件和旁车 JSON。文件 Key 只用于缩小候选集合，命中后仍完整比较冻结身份；解析失败继续返回错误，不因复用或 Key 相等放宽授权。

媒体目录首次计划保存根目录身份、冻结政策、已知成员和操作记录，不强制保存全部陌生文件的清单或为其伪造 owner。115 正常目录操作采用“明确删除成功响应＋按原目录 ID 确认不存在”的完成依据，覆盖的已知成员记录为随目录操作完成，不再逐成员回查。它不是每个历史文件 ID 在网盘任意位置均不存在的独立证明。首次核验目录已经不存在，或上次响应不明后仅确认目录缺失，都不能直接生成全部成员完成结果，仍须按原身份分别确认已知目标。超时、部分失败、目录仍在或身份冲突时也复核原目录及已知目标；没有完整树快照时不承诺逐陌生成员恢复。不能可靠重新确认冻结范围与当前保护时保留异常，必要时仅处理独立授权的已知文件，不盲目重发整目录、不追随移动目录或同路径替换对象。

首次构建计划时父目录清单不可取得，也允许对冻结的视频、历史旁车候选及已纳入范围的元数据执行只读缺失确认。仍须核验服务器、原 Emby 条目／STRM、授权、领取和代际；只有该目录全部已知目标的原稳定 ID 都明确不存在，才原子保存计划和 `already_absent` 结果，随后处理其他完整目录。此路径不发送删除，不把历史候选提升为可删除旁车。任一原对象仍存在、移动、身份冲突或查询失败时不保存不完整计划，重试重新建立完整清单。115 和百度支持原稳定 ID 确认；OpenList 无此独立定位能力时继续保留待核验。

115 删除专用详情入口只将完整且一致的结构化缺失响应解释为原对象不存在，跳过普通重试及最终 ERROR；普通详情调用方的重试策略保持。网络／权限／限流、缺字段或矛盾响应不视为不存在。删除请求在队列真正发送前重新运行最终检查，校验失败不发送、不自动重放。百度目录同时核对完整路径与原 fsid，路径缺失不能替代原 ID 确认；OpenList 使用明确文件批量，不启用目录整删。

一轮 Emby 核验复用存在外部变化的时效窗口；目录 API 也不能原子约束最后读取之后的外部写入或移出。实施和验收必须分别记录这些限制，不能承诺零竞态或固定完成秒数。

删除执行仅接受版本 2 清理政策和版本 2 元数据封装。缺失、旧版或未知政策的可执行收件保持 `unresolved`；冻结成员包含旧旁车数组、损坏数据或未知元数据版本时，拒绝构建及执行计划，也不清理本地关联，不自动改写为当前格式。现有本地 STRM／元数据对账与上传策略保持原义，不自动补删历史残留。持久格式说明见 [Emby 身份与事件存储](../reference/database-schema.md#emby_index_statesemby_item_statesemby_item_evidences)。

## 同步运行状态

`GET /api/{emby|jellyfin}/sync/status` 成功读取快照返回 HTTP `200`；尚未配置也是成功查询，`data.exists=false`。配置或条目数量查询遇到数据库故障返回 `500`、`INTERNAL_ERROR`，不能据此判断未配置。

状态接口返回的核心字段：

| 字段 | 含义 |
| --- | --- |
| `is_running` | 是否有本端条目同步任务运行 |
| `sync_mode` | 当前或最近一次模式 |
| `started_at` | 当前任务开始时间 |
| `last_sync_time` | 最近一次成功同步时间 |
| `last_success_sync_mode` | 最近一次成功同步模式 |
| `last_full_sync_at` | 最近一次成功全量同步时间 |
| `last_incremental_sync_at` | 最近一次成功增量同步时间 |
| `last_saved_cursor_at` | 增量同步游标 |
| `last_processed_count` | 最近一次处理数量 |
| `last_error` | 最近一次失败原因 |
| `total_items` | 本端本地已同步 item 数 |

如果已有任务运行，定时任务直接跳过，不排队堆积。手动全量同步遇到运行中的任务时，前端应提示稍后再试。

Web 设置页由 `api/mediaLibrary.ts` 封装两端配置、媒体库、提取和同步请求，`useMediaLibrarySyncStatus` 管理本端轮询与过期回调。隐藏标签暂停轮询，返回只重读状态，不覆盖草稿。保存失败保留输入，公共请求分类见 [前端开发约定](../engineering/frontend-development.md#api-响应与请求错误)；动态 `last_error` 不直接展示底层错误内容，页面提示查看服务日志。

“提取媒体信息”扫描本端全部媒体库，不受索引选库范围和入库自动提取分项限制。每端同一时间只运行一轮，后台扫描结束才释放运行标记；用户必须具备全部媒体库与播放权限。缺少可用媒体流的条目进入原下载队列，来源为 `emby_media` 或 `jellyfin_media`。普通索引查询不增加提取专用媒体流字段。

手动提取受理返回 HTTP `202` 和 `data.status="submitted"`；本端未启用、连接未配置完整或已有提取任务运行返回 `409`、`MEDIA_LIBRARY_UNAVAILABLE`。读取配置的数据库故障返回 `500 / INTERNAL_ERROR`，诊断保留原始原因，不作为配置或运行状态冲突。受理后的扫描失败仍由后台任务处理，不回写已返回的受理响应。

新提取任务以 `source`／`source_type=emby_media|jellyfin_media` 保存归属，持久化隐藏的 `emby_item_id`、`media_server_id`，不保存新的地址／密钥；重试只允许同端同实例更换当前地址／密钥，不能把旧任务投向另一实例。旧任务无法证明原身份时不自动替换凭据。只有 HTTP 200、合法 JSON、无 `ErrorCode` 且具备适用主流 codec 才能完成；非成功 HTTP、JSON 错误及无可用媒体流不能标记提取成功；自动单条入队只忽略活跃重复任务，其他失败记录日志。队列字段见 [下载任务](../reference/database-schema.md#db_download_tasks)。

程序启动并完成数据库迁移后，会分别清理两端上次进程异常退出遗留的 `is_running=true` 状态，避免全量、增量和 Webhook 单条同步长期被旧运行标记阻塞。该清理只复位 `is_running`、`sync_mode` 和 `started_at`，并写入 `last_error` 说明原因；不会推进或清空 `last_sync_time`、`last_full_sync_at`、`last_incremental_sync_at` 和 `last_saved_cursor_at`。

## 升级和迁移说明

当前 schema 为 71；媒体库结构变更与旧关联字符串转换一并在 70→71 事务中完成。新库直接建立两份默认关闭的配置；升级已有 Emby 配置设置 `enabled=true`、`enable_media_notification=1`，其他原连接及功能值保留，Jellyfin 默认关闭且不继承旧连接。旧 Emby 地址实际指向 Jellyfin 时不自动搬迁，用户需在对应标签手动配置。

两端配置状态、业务归属与复合键见 [媒体业务归属](../reference/database-schema.md#媒体业务归属)，完整初始化、迁移及归档版本规则由数据库文档维护。

版本 65→66 在一次事务中新增物理快照、成员、身份状态、旁车历史、持久收件和逐目标结果，保留旧媒体及关联记录；完整迁移与失败回滚约定见 [数据库 schema 与迁移](../reference/database-schema.md#迁移与初始化)。旧索引不从当前同名文件推断过去的删除身份。升级后建议先手动执行一次全量同步，用于建立本地索引和全量批次标记。默认启用每日首次定时全量同步，之后 Cron 会在每天首次成功全量后按增量同步兜底变更。

## 不变量

- Emby 网页连接应用只影响后续请求；旧 HTTP／WebSocket 保留其会话，授权和缓存不能跨连接配置复用。共享状态锁不跨 SQL、网络、流式转发或退出等待。
- 通知媒体服务器刷新与读取本端本地索引是两条独立链路，入口和状态不得混用。
- 配置、索引、同步水位、刷新任务和删除证据按固定媒体类型隔离；普通查询不能省略或猜测类型。
- 新配置默认关闭，关闭通知只停止发送；入库自动提取分项不能阻止手动提取。
- 同类型原 ServerID 不匹配时不能向新实例重放旧提取、刷新或删除工作；冻结身份和授权不被新设置扩大。
- 刷新统一写入 `emby_library_refresh_tasks` 并由协调器执行，生产链路不得直接调用旧的立即刷新函数。
- 非 Webhook 任务仅在 STRM 实际变化后请求刷新；Webhook 默认不刷新，只有显式 `refresh_emby=true` 且满足变化条件时才提交。
- 批量和目录扫描父任务仅在全部子任务成功且有变化时提交累计集合；单项双端解析部分失败时，已核验的另一端可先经协调器投递，任务仍保留失败。
- item 目标优先，可靠证据不足时才回退到关联媒体库；多库且无可靠证据时保持 unresolved，不任选媒体库。

## 验证方式

- Emby 设置应用运行[网页设置应用验证](../engineering/verification.md#网页设置应用验证)，覆盖同一监听启停／换连接、旧 HTTP／WebSocket、授权与缓存隔离、绑定失败重试、迟到应用和最终停止。真实播放器效果单独验收。
- 运行上述验证说明中的后端、前端命令；改动刷新协调器时至少覆盖 item 目标、媒体库回退、去抖、下载等待和父子任务失败场景。
- 修改迁移字段时运行 `(cd backend && go test ./internal/models/)`，并核对 [数据库 schema 与迁移](../reference/database-schema.md) 的版本和字段说明。
