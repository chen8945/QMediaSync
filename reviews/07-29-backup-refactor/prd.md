## 范围内需求

### R1. 恢复生命周期、维护屏障与 HTTP 一致性

1. 恢复成功、自动回滚成功或回滚失败时，旧进程在 HTTP 服务停止接受业务请求前必须始终保持业务维护屏障；状态查询仍是唯一允许的业务状态接口。
2. 维护切换必须拒绝新业务处理器，并等待此前已经通过维护中间件的业务处理器退出，才可导出、创建恢复快照或覆盖数据库/白名单文件。
3. 恢复在快照就绪前失败或 panic 时，必须先持久化终态并按终态维护语义切换，再恢复任务准入、Cron 和 worker；不得在维护仍拒绝 HTTP API 时先启动后台工作。
4. 手动备份和手动恢复在发现已运行任务时仍应返回现有 HTTP `409`，而不是先返回 `202` 再无限等待一个在受理窗口中进入的任务。
5. 恢复确认必须只在实际取得恢复操作执行权时消耗 `preflight_id`；若协调器被并发操作占用，原预检记录仍可在有效期内重试。

### R2. 任务准入与实际静止

1. `POST /api/setting/threads` 在任务准入关闭期间必须不写设置、不替换下载队列，并以既有维护窗口语义拒绝；在正常运行时替换队列前必须停止并等待旧队列已派发 worker 退出，不能使其脱离 `StopAndWait`。
2. `POST /api/setting/emby/parse` 和 `StartParseEmbyMediaInfo` 必须参与共享任务准入。准入关闭时不得启动新的远程遍历 goroutine；已启动的工作必须可被维护等待逻辑观察或完成后才被视为静止。
3. 不得损害已有同步、目录上传、STRM、Emby item 同步、传输队列和 Cron 的准入行为。

### R3. PostgreSQL 恢复、迁移与重试

1. PostgreSQL 恢复对原本为空或部分初始化的目标创建表后，如果任意导入、序列、配置或日志步骤失败，自动回滚必须恢复**数据和 schema**到快照时的准确形态：快照中不存在的应用表不能残留。
2. 失败后的空 PostgreSQL 目标必须仍可走正常首次初始化流程，不能因残留空 `migrator` 表跳过默认记录和迁移版本初始化。
3. SQLite→PostgreSQL 迁移中，导入后所需的 schema/部分唯一索引修复失败必须是可观察错误：保留 `backups/migrate.zip`、阻止业务运行时启动，且不会把失败误报为完成并删除工件。
4. 成功迁移必须在删除 `migrate.zip` 前完成所有表导入、必需后处理和 PostgreSQL 序列修复；后续插入不得与已迁入主键冲突。

### R4. 备份工件容量与未加密工件安全边界

1. 恢复预检的磁盘空间计算必须覆盖已验证内层 ZIP 的实际解压体积、临时切换文件、预恢复快照和目标数据库所需空间，不能只按压缩 `payload.bin` 长度通过。
2. 当前未加密 v1 工件允许继续恢复，但界面和文档必须明确：当前散列/三方密钥指纹只能发现意外损坏或不一致，不能在工件本身包含 `config/encryption.key` 时验证可完全重写容器的攻击者。
3. 已加密 v1 工件的 AES-GCM 认证、密码兼容性和现有恢复能力不得退化。
4. 后续真正的明文工件认证格式必须使用**不进入工件、不随恢复覆盖**的本机签名密钥；不在本任务中实现该新格式。

### R5. HTTP、CORS、上传边界与前端状态

1. 已配置可信跨域来源的浏览器必须能在 CORS 预检后发送 `X-Backup-Operation-Token` 轮询 `GET /api/backup/status`。
2. 上传恢复在 Gin/net/http 解析 multipart 表单前必须限制请求体为工件最大大小加明确的 multipart 开销；暂存层的 1 GiB 限制继续作为第二层防御。
3. 备份记录页面在可见且激活时收到手动备份终态，必须重新获取权威 `/api/backup/list` 快照，从而显示新记录和 `latest_operation`；隐藏、卸载、正在加载时保留既有无重叠和清理语义。
4. `validateBackupPassword` 必须与 Go `unicode.IsSpace` 的行为一致，至少覆盖 U+0085 与 U+FEFF 的分歧，并继续按 Unicode code point 计数、不裁剪、不归一化。

## 用户补充问题（待源码复核后纳入确认清单）

1. **备份记录页面**
   - 移除“手动备份”按钮外的灰色操作框。
   - 最近一次操作信息必须明确展示操作类型、结果状态和完成时间；按状态使用语义标签色；容器宽度随内容自适应，不能使用不必要的固定宽度。

2. **恢复后认证状态**
   - 恢复结束后，仍处于旧会话的浏览器应在可用的认证检查时立即被引导到登录页，不依赖手动刷新或切换页面。

3. **备份配置页面**
   - 核实 `/api/setting/cron?cron=...` 是否只有备份配置页用于预览下次执行时间；若无其他消费者且可通过本地确定性计算/既有组件替代，评估移除或收敛该请求，而不是仅因路径名称删除仍有用户价值的能力。
4. **文案与日志**
   - 润色最新提交新增或修改的前端备份文案和日志，避免不必要的专业术语，以简短、清楚、面向普通用户的中文说明结果、下一步和风险；不得减少诊断所需的稳定错误码或安全信息。

- 正确性、数据完整性、安全和可恢复性优先于风格或广泛重构。

- PostgreSQL 15 Docker 验证使用现有 `postgres:15-alpine`，短生命周期、隔离用户/数据库、动态本机端口或隔离网络；不在主机安装 PostgreSQL。
- 用户已于 2026-07-29 授权创建并清理该验证容器和全部临时测试数据。
- 未加密 v1 工件采用兼容策略：继续允许恢复，但必须提示它只能检测偶然损坏、不能认证抗篡改完整性；未来新格式使用不进入工件的外置签名密钥。

## 风险与延后验证

- PostgreSQL 15 验证能覆盖最低支持版本的事务、清表导入、回滚、序列和迁移包重试，但不能证明其他 PostgreSQL 大版本的兼容性；实际部署固定于其他版本时仍应补验。
- 真实部署中的进程退出与平台重启衔接、持久卷权限和反向代理行为需在 Docker/systemd/FNOS 隔离环境手工检查。
- 全量 controllers `-race` 存在既有凭据会话时序超时；最终报告需列出实际使用的定向命令与该基线限制。
