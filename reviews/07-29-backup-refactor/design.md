# 审查并修复最新备份恢复提交：技术设计

## 范围与设计原则

实现以 `dd4795a^..dd4795a` 的已确认缺陷为界。保持现有路由、已加密 v1 工件、状态响应字段和调用模式；只在错误状态、维护时序、资源边界或已声明兼容约束被违反时修改行为。

所有写入共享运行时状态的修复由同一实现链顺序提交；并行代理只用于只读探索和补丁后的独立复审，避免恢复、协调器、队列和前端状态文件发生并发冲突。

## 一、维护窗口是三阶段屏障

### 所需状态模型

```text
正常运行
  │ 关闭任务准入
  ▼
等待静止
  │ 拒绝新的业务 HTTP 请求，并等待已进入的业务处理器
  │ 停止并等待 worker，等待持久化任务计数归零
  ▼
维护中
  │ 执行导出，或创建快照/应用恢复/回滚
  ▼
终态
  ├─ 备份：发布终态，解除维护，恢复任务准入
  └─ 恢复：持久化终态并保持业务维护，直到 HTTP 关闭开始
```

### 契约

1. 在维护标志切换前进入的请求拥有有限期的处理中租约。进入维护时先拒绝后续业务请求，再等待已有租约归还，之后才允许读取或写入业务状态。
2. 静态资源和精确的 `GET /api/backup/status` 仍为例外。状态处理器只访问外部操作状态，不得取得业务处理器租约。
3. 手动备份/恢复必须在返回 HTTP `202` 前同步关闭任务准入。如果已有已登记任务或准入租约，解除短生命周期屏障并返回既有 `409`；定时备份保留允许等待 30 分钟的策略。
4. `taskBarrier.Resume` 只允许在终态维护状态已经持久化后调用。恢复成功不会恢复 worker，因为旧进程即将退出；快照就绪前的恢复失败必须先发布终态再恢复。回滚路径在终态持久化后退出，绝不能重新开放业务流量。
5. 协调器取得执行权与预检记录消耗必须构成可回退的整体。协调器失败时预检记录保持有效；不得在昂贵的工件校验或数据库探测期间持有短临界区锁。

### HTTP 准入机制

新增由维护中间件/协调器边界拥有的维护请求闸门：

- 正常业务请求在确认闸门未关闭后取得读租约；
- 进入维护时设置关闭状态，取得写侧并等待所有已进入租约归还；
- 例外路由绕过该租约，保持既有状态/静态资源语义；
- 终态恢复在 `QMSApp.Stop()` 开始关闭 HTTP 前不重新打开闸门；终态备份和安全的快照前恢复失败只在对应终态切换后重新打开。

实现必须避免“操作请求等待自身租约”的死锁。操作入口在同步安装屏障后、等待历史请求前必须释放自身处理器租约；或者闸门 API 以明确设计排除发起者租约。

## 二、任务准入与队列所有权

### 下载队列替换

`Settings.UpdateThreads` 当前写设置后调用 `InitDQ`，而后续直接 `UpdateGlobalDownloadQueueConcurrency` 只保护新指针。改为一条受任务闸门保护的完整更新路径：

1. 在写设置或改变队列所有权前取得任务准入；
2. 仅在准入持有期间构造/配置替换队列；
3. 发布新的 `GlobalDownloadQueue` 前停止并等待旧队列；
4. 只有准入仍开放时才原子发布并启动替换队列；
5. 准入关闭时返回可识别的冲突，不写设置、不变更全局指针。

旧队列必须在 `StopAndWait` 返回前保持可访问。维护窗口以外既有更新/重启语义保持不变。

### 手动 Emby 解析

`StartParseEmbyMediaInfo` 必须在设置运行标记和启动 goroutine 前取得任务准入。其准入租约必须保留到可观察的运行状态或明确的 waitgroup/生命周期计数登记完成；维护屏障的 Emby 运行中判定必须包含它。若不使用持久化登记，则屏障拥有进程内解析 waitgroup/计数。

## 三、PostgreSQL 恢复快照正确性

### 快照表达

`restoreSnapshotMeta.PostgresTables` 已记录快照时存在的表，把它作为 schema 形态的权威来源：

- `capturePostgres` 记录恢复前存在的每一个目录表；
- `rollbackPostgres` 计算目录中不在该集合的表；
- 在同一个回滚事务中，只清空/导入快照前存在的表，并按反向目录顺序删除恢复期间新建的表；
- 仅为仍存在且从快照恢复的表修复序列。

该设计把空目标恢复为真正的空，把部分目标恢复为相同的部分 schema。每一项清空、删除、导入和序列操作必须使用事务绑定的 GORM 连接，依赖 PostgreSQL 的事务性 DDL。

### 恢复测试切面

不引入仅用于测试的生产行为。包内测试可创建快照、调用 schema 准备以重现新建表、调用 `Rollback`，再断言表存在性和原有记录。真实 PostgreSQL 集成测试验证同一契约的 DDL 语义。

## 四、SQLite→PostgreSQL 迁移完成语义

`importMigrationArchive` 在事务中提交 schema 准备、导入和序列修复，之后调用 `migrateImportedDatabase`。每个必要的导入后修复必须提供可返回错误的契约。

- 提取显式的“确保已导入数据库当前 schema”错误返回辅助函数，首先覆盖活跃传输任务部分唯一索引及其他不由 `migrateTargetSchema` 保证的导入后不变量。
- 在删除 `migrate.zip` 前调用该函数。
- 失败时保留工件、向 `main.go` 返回阻断启动的错误。下一次启动从完整工件重新执行。
- 不得在相关工作确实位于事务中之前声称已提交数据会回滚。重试契约必须明确且幂等：下一次导入会在事务中安全清空并替换目录数据。
- 不对所有历史 `models.Migrate()` 分支作无关重写；最小修复目标是让已确认的索引/schema 错误可观察，并用同一错误返回辅助函数保护后续导入后要求。

## 五、工件资源预留与明文真实性边界

### 资源预留

内层验证已检查每个 ZIP 条目及总 `UncompressedSize64`。扩展 `VerifiedArtifact` 或已验证清单投影，记录该已验证的物化大小。恢复目标检查按同时占用的最大空间计算：

```text
已验证内层归档物化空间
+ 快照数据库 / 当前 SQLite 数据库或 PostgreSQL 导出
+ 暂存白名单文件（包含日志）
+ 临时目标数据库、切换文件和安全余量
```

使用检查过的整数运算，并保持 `ErrRestoreInsufficientSpace` 的稳定映射。不得用数 GiB 实际解压构造测试；通过已验证大小投影或表驱动容量计算证明逻辑，不制造资源耗尽测试。

### 未加密 v1 工件策略

用户已选择兼容策略：未加密 v1 工件继续允许恢复，但必须明确提示其只检测偶然损坏，不能认证抗篡改完整性。

对嵌入的 `config/encryption.key` 做 HMAC 无法提供真实性，因为能读取工件的一方也能重算 HMAC。未来认证明文工件应创建新格式/版本：使用不在恢复白名单内的本机签名密钥，对不可变 header/payload 元数据签名，并显式定义旧格式行为。本任务不实现该新格式，也不得把旧散列表述为真实性证明。

## 六、HTTP 和前端边界

### CORS 与上传大小

- 在可信来源 CORS 允许请求头中加入 `X-Backup-Operation-Token`，并对 OPTIONS 预检断言该响应头。
- 在任何 `ShouldBind`/`FormFile` 前设置 `http.MaxBytesReader` 风格的请求体限制。限制允许 1 GiB 工件和已记录的小型 multipart 外壳；当 `Content-Length` 存在且超限时提前拒绝，但绝不依赖它处理 chunked 请求。
- 保留 `StageUploadArtifact` 的既有大小限制和清理逻辑作为第二层防御。

### 记录刷新与校验一致性

- 通过备份 store 暴露终态操作通知，或在活动组件监听稳定终态切换；活动且可见时调用现有权威 `refreshBackupRecords`。重置轮询状态前必须保证刷新已排程，隐藏或卸载后的回调不得发起请求。
- 用与 Go `unicode.IsSpace` 完全对应的显式 Unicode code point 谓词/集合替换 JavaScript `\s`；后者相对 Go 会错误拒绝 U+FEFF、漏掉 U+0085。

## 兼容性与回滚

- 保留加密 v1 工件恢复和现有 HTTP 响应字段。
- 明确未加密 v1 工件不能提供抗篡改认证；未来外置签名密钥格式不属于本任务。
- 所有补丁保持局部、可审查；不使用破坏性 Git 命令，不修改无关工作区内容。
- 短生命周期 PostgreSQL 环境绝不接收生产数据或凭据；即使断言失败或中断，也通过 `defer`/shell `trap` 删除容器和存储。
