普通更新和旧内嵌 PostgreSQL 迁移是两件事。已经使用 SQLite 或独立 PostgreSQL 的实例，可以按前半部分更新；还在使用旧内嵌 PostgreSQL 的实例，需要先完成后半部分的数据迁移。

## 下载 Beta 测试版

Beta 提供 Windows、Linux 和飞牛各两种架构的完整安装包，适合需要验证尚未正式发布改动的用户。安装或覆盖现有版本前，先按下一节备份数据库和配置。

1. 登录 GitHub，打开 [Beta 构建页面](https://github.com/chen8945/QMediaSync/actions/workflows/beta.yaml)。
2. 选择对应 `dev` 提交且构建成功的运行，进入页面下方的 **Artifacts**。
3. 按系统和架构下载下面的完整安装包。`web-statics`、`linux-binary-*` 是构建中间文件，安装时不选它们。

| 系统 | x86-64 | ARM64 |
| --- | --- | --- |
| Windows | `QMediaSync_<版本>_windows_x86_64.zip` | `QMediaSync_<版本>_windows_arm64.zip` |
| Linux | `QMediaSync_<版本>_linux_x86_64.tar.gz` | `QMediaSync_<版本>_linux_arm64.tar.gz` |
| 飞牛 | `QMediaSync_<版本>_fnos_x86_64.fpk` | `QMediaSync_<版本>_fnos_arm64.fpk` |

`<版本>` 例如 `0.14.15-beta.20261025103000.g1a2b3c4`，包含基础版本、UTC 构建时间和源码提交号；同一次构建的各平台版本一致。下载得到的就是 ZIP、tar.gz 或 FPK 文件。Windows / Linux 完整解压后按对应安装页启动；飞牛通过应用中心“手动安装”选择 FPK。

Beta 包不在 Releases 页面提供，也不会由 QMediaSync 的在线更新自动获取。Actions 产物默认保留 90 天，维护者可以调整；到期或被删除后需选择新的成功构建下载。飞牛 Beta 与正式版共用同一应用和数据目录，覆盖升级前同样需要备份；回退时按下文处理配套数据库。

## 更新前先保留这些东西

1. 在「系统设置 → 版本更新」查看并记下当前版本，阅读目标版本的更新说明。
2. 按 [备份与恢复](备份与恢复.md) 生成并下载数据库 ZIP；另行保留整个 `config/`，尤其是 `encryption.key`。
3. 保留原版本安装包或镜像版本，以及本地 STRM、元数据和媒体文件。使用外部 PostgreSQL 时，不能把 QMediaSync 的 `config/` 副本当作 PostgreSQL 数据目录的备份。
4. 安排好正在进行的同步、上传和下载，再开始更新。

程序升级可能修改数据库结构。需要退回旧版本时，除了程序，还可能需要恢复**更新前与旧版本配套的数据**；不要直接让旧程序读取已经升级过的数据库。

## Docker Compose 更新

建议通过更新镜像来更新 Docker 部署，便于下一次重建容器时继续使用同一版本。

在原 Compose 文件目录操作，以下示例服务名为 `qmediasync`：

1. 固定版本部署先把 `image` 改为目标标签，例如 `ghcr.io/chen8945/qmediasync:v<目标版本号>`；使用 `latest` 时保持原标签。
2. 拉取并重新创建 QMediaSync 服务：

```bash
docker compose pull qmediasync
docker compose up -d --no-deps qmediasync
docker compose logs --tail=100 -f qmediasync
```

3. 日志没有连续启动失败后，打开管理页面，检查「系统设置 → 版本更新」显示的版本是否为目标版本，并核对账号和同步目录。

原部署用了 `-f`、`-p` 或 `--env-file` 时，以上命令也要带上原参数。保留原来的 `config/`、媒体目录挂载和 PostgreSQL 数据卷；更新 QMediaSync 不需要同时更换 PostgreSQL 大版本。

使用 `docker run` 的部署，先记下原容器的镜像、端口、挂载、网络和环境变量，再用新镜像按同样参数重建 QMediaSync 容器。尤其要确认新容器仍挂载**原来的配置目录**，否则看起来会像全新安装。

Docker 也可能支持网页中的「在线更新」，但它更新的是当前容器中的程序文件，不会改 Compose 的镜像标签。之后重新创建容器，会再次使用该标签对应的镜像版本；使用镜像方式更新更容易保持版本一致。

## Windows 手动更新

1. 从 [QMediaSync 发布页面](https://github.com/chen8945/QMediaSync/releases) 下载对应架构的 Windows 发布包，解压到临时目录。
2. 从托盘退出正在运行的 QMediaSync。
3. 用新包的 `QMediaSync.exe` 和整个 `web_statics/` 替换安装目录中的旧文件，保留原 `config/`。
4. 重新打开 `QMediaSync.exe`，查看启动结果，再登录网页核对版本和数据。

不要只替换程序、留下旧前端文件，也不要把新的空 `config/` 覆盖到原配置目录上。架构选择见 [Windows 安装使用](Windows-安装使用.md)。

## Linux 手动更新

下面假设安装目录是 `/实际安装目录`，使用 `qmediasync.service`。将路径改为自己的位置，先把匹配架构的新发布包解压到**另一个临时目录**。

1. 停止服务：

```bash
sudo systemctl stop qmediasync
```

2. 在文件管理器或终端中，将安装目录里的旧 `QMediaSync` 和 `web_statics/` 移到备份位置，再把新包中的这两项复制到安装目录。保留原 `config/`，并保证原服务用户能读取程序、写入配置和媒体目录。
3. 给新程序添加执行权限并启动：

```bash
chmod +x /实际安装目录/QMediaSync
sudo systemctl start qmediasync
systemctl status qmediasync --no-pager
sudo journalctl -u qmediasync -n 100 --no-pager
```

4. 登录网页，检查实际版本、账号、同步目录和关键设置。

直接运行程序时，先结束原进程，替换同样的两项文件，再按原方式启动。安装和 systemd 使用见 [Linux 安装使用](Linux-安装使用.md)。

## 原生 fnOS 更新

原生 FPK 应用不通过 QMediaSync 网页“在线更新”安装新版本。

- 应用中心安装的版本，在飞牛应用中心查看是否有更新；是否已上架及可更新版本，以平台实际显示为准。
- 手动安装的版本，从 [QMediaSync 发布页面](https://github.com/chen8945/QMediaSync/releases) 下载与设备匹配的较新 FPK：x86-64 使用 `QMediaSync_fnos_x86_64.fpk`，ARM64 使用 `QMediaSync_fnos_arm64.fpk`。在应用中心选择“手动安装”并上传即可升级，无需先卸载；相同或更低版本会被平台拒绝。不要把 Linux 压缩包当作 FPK 上传。

更新前备份并保留原应用共享目录中的整个 `config/`。不要为更新而直接删除应用数据；确需卸载重装时，保留卸载向导的默认“保留数据”选项。更新或重装后检查版本、账号和同步目录是否保留；如果突然要求重新配置数据库，先停止应用检查原配置，不要直接初始化。

发布附件中的 `checksums.txt` 包含 FPK 的 SHA-256，可用于核对下载文件。它不会在 QMediaSync 网页安装 FPK，也不代表飞牛应用中心会自动读取这个文件。

日常重启在飞牛应用中心停止后启动。首次配置后的自动启动不改变恢复流程，备份恢复后仍需按页面提示手动重启。安装、授权和数据位置见 [飞牛安装](飞牛安装.md)。

## 网页在线更新

支持在线更新的环境，可以打开「系统设置 → 版本更新」，展开目标版本的说明，点击「在线更新」。等待下载、安装和重新上线后，再核对页面上的当前版本。

| 运行方式 | 更新方式 |
| --- | --- |
| Windows 发布版 | 支持在线更新，也可按上面步骤手动替换 |
| Docker 默认入口 | 支持的入口可接收更新包并重新启动程序；长期版本管理建议仍用镜像更新 |
| 已正确启用在线更新的 systemd 服务 | 支持；服务用户需要有安装目录写权限 |
| 手动运行或未启用相应支持的 Linux 服务 | 使用手动更新；本 Wiki 的 Linux 自建服务示例采用这种方式 |
| 原生 fnOS FPK | 使用飞牛应用中心或对应架构的 FPK，网页不提供在线安装 |

页面提示不支持当前运行方式时，按部署方式手动更新即可。提示缺少校验文件或校验失败时，不要跳过校验强行替换；可重新下载目标发布包，确认下载完整。

在线更新提示已经重启，不等于目标版本一定启动成功。若一直无法访问，查看容器或服务日志；systemd 可能会不断重试新程序，并不会因为启动失败就自动退回旧版。

## 先判断是不是旧内嵌 PostgreSQL

查看原来正在使用的 `config/config.yaml` 或 `config/config.yml`。下面的组合表示旧内嵌 PostgreSQL：

```yaml
db:
  engine: postgres
  postgresType: embedded
```

`engine: sqlite` 表示 SQLite；即使旧文件残留未使用的 `postgresType: embedded`，也不因此变成内嵌 PostgreSQL。

当前版本不包含内嵌 PostgreSQL，也不会自动处理旧迁移包。出现以下情况时，程序会拒绝继续：

- PostgreSQL 配置仍写着 `postgresType: embedded`。
- 实际配置目录下存在未处理完的 `backups/migrate.zip`。
- 主配置不见了，但还留着旧的 `config/postgres` 数据目录。

遇到这些提示，应保留全部原文件，回到兼容旧数据的版本完成迁移。删除旧目录、删掉迁移包或直接把 `engine` 改成 `sqlite`，都不会把旧数据搬过来。

## 从旧内嵌 PostgreSQL 迁移

已经核对过的过渡版本包括原项目 `v0.14.23` 和本项目 `v0.15.17`。下面以本项目 `v0.15.17` 的迁移向导为例。它先把内嵌 PostgreSQL 导出，再导入**独立的 PostgreSQL**，不能直接转成 SQLite。

完整顺序是：

**旧内嵌 PostgreSQL → 过渡版本迁入独立 PostgreSQL → 用当前版升级并核对 → 如需 SQLite，再生成当前格式备份迁移。**

### 1. 保存能回到原状态的副本

1. 停止旧 QMediaSync，保存实际使用的整个配置目录，包括内嵌 PostgreSQL 数据、密钥和其他配置；保留原版本程序或镜像。
2. 同时保存媒体目录，并记录当前账号、同步目录、重要设置和业务记录数量，便于迁移后逐项核对。
3. 保留一份不再改动的停机副本。后续用来迁移的目录和这份副本分开存放，不要让两个实例同时打开同一内嵌数据目录。

### 2. 准备独立 PostgreSQL

按 [Docker 安装](Docker安装.md) 或 [Windows 安装使用](Windows-安装使用.md) 中的数据库说明，准备 PostgreSQL 15 及以上的独立服务，给 QMediaSync 使用单独的空数据库，并确认从迁移程序所在环境能够连接。

记下主机、端口、用户名、密码和数据库名。Docker 容器中的 `127.0.0.1` 指容器自身；数据库在其他容器时，应使用可达的服务名或地址。不要用其他应用的数据库作为迁移目标。

这个过渡版向导会用未加密连接测试 `postgres` 数据库，目标需要允许迁移程序这样连接，并允许该用户访问 `postgres`。只接受 TLS 加密连接的数据库不能直接使用这个旧向导；可以先迁到受控的本机或容器网络中的临时 PostgreSQL，升级并核对后，再按当前版本的备份恢复流程迁往最终数据库。

### 3. 用过渡版本完成导出和导入

1. 从 [v0.15.17 发布页面](https://github.com/chen8945/QMediaSync/releases/tag/v0.15.17) 取得对应程序或镜像，沿用旧实例的配置和数据挂载启动。遇到无法读取旧数据库的错误时先停止，保留日志，不要强制重新初始化。
2. 检测到内嵌 PostgreSQL 后，程序会进入迁移向导。按启动日志给出的地址打开页面，点击「开始备份」。
3. 等待导出完成，确认实际配置目录中生成 `backups/migrate.zip`，并把这个 ZIP **另外复制一份到外部备份位置**。
4. 在向导中填写独立 PostgreSQL 的连接信息，点击「测试连接」。连接通过后，点击「保存配置并退出」。
5. **仍然使用同一个过渡版本重新启动。** 配置已经改为独立 PostgreSQL，这次启动会读取 `migrate.zip` 并导入；容器有自动重启策略时，应确认重新起来的仍是过渡版本。
6. 保留这一轮完整日志，等待导入结束并检查网页。程序会在完成流程后删除工作目录中的迁移 ZIP，所以第 3 步的外部副本要提前保留。

不要在「保存配置并退出」后直接换成当前版本。当前版本不会替过渡版本完成导入，也不能把旧 `migrate.zip` 上传到「备份恢复」来代替这一步。

### 4. 核对后再升级

旧迁移工具会在部分表导出或导入失败时记录错误后继续。因此，页面显示完成或 `migrate.zip` 已消失，都不能单独证明数据完整。

至少核对：

- 日志中有没有导出、导入、数据库连接或表处理失败。
- 管理员是否能登录，网盘账号数量及授权状态是否正确。
- 同步目录、本地路径、刮削、通知和媒体服务器设置是否保留。
- 重要任务、同步记录和其他业务记录的数量是否符合迁移前的记录。
- 需要的 QMediaSync API Key 是否可用，两步验证是否仍按预期工作。

旧导出格式可能没有保存 API Key 的完整验证信息和两步验证密钥，可能需要重新创建 API Key、更新 Webhook 等调用方，并重新设置两步验证。这些遗漏不能靠后续再生成一个备份自动补回。

确认独立 PostgreSQL 中的数据可用后，先为这份数据库留好备份，再停止过渡版本，按本页的普通更新步骤切换到当前版本，继续连接**刚迁入的同一份独立 PostgreSQL**。当前程序会按支持的升级规则更新数据库结构；启动失败时先保留现场和日志，不要重新运行空库初始化。

当前版启动并再次核对无误后，按 [备份与恢复](备份与恢复.md) 生成新的数据库 ZIP。想改用 SQLite 时，再按该页的跨数据库迁移步骤恢复到独立的 SQLite 目标。

旧内嵌目录和停机副本在核对结束前始终保留。旧数据目录不会被当前程序自动删除；确认已有可用备份且数据完整后，再自行归档处理。

## 更新后出现问题

| 现象 | 先检查什么 |
| --- | --- |
| 打开后变成首次安装或要求创建管理员 | 是否挂载了错误的 `config/`，是否指向空数据库；先停止并检查，不急着重新初始化 |
| 提示内嵌数据库或迁移包未处理 | 按本页旧版迁移步骤回到过渡版本处理，保留旧目录和 ZIP |
| 网页还是旧版本、部分页面报错 | 程序和 `web_statics/` 是否一起更新，Docker 是否仍使用旧镜像，浏览器刷新后实际版本是否正确 |
| 更新后两步验证无法使用 | 原 `encryption.key` 是否保留，系统时间是否正确；确实无法登录时见 [管理员与密码恢复](管理员与密码恢复.md) |
| 新版本不断启动失败 | 查看日志，保留当前状态；需要回退时一起考虑程序与更新前数据库，不让旧程序直接读取已升级数据库 |

当前备份恢复、数据库修复和旧内嵌迁移各有用途。对应操作见 [备份与恢复](备份与恢复.md)，不要把数据库修复当作数据迁移或版本回退。
