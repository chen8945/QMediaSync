备份管理用于保存和恢复 QMediaSync 的数据库。换机器、换数据库或升级前，建议同时准备 **数据库备份 ZIP、原来的 `config/` 目录，以及媒体文件的独立备份**。这三样保存的内容不同，不能相互替代。

## 先弄清楚备份保存了什么

| 内容 | QMediaSync 生成的数据库 ZIP 是否包含 | 你还需要做什么 |
| --- | --- | --- |
| 管理员、网盘账号、同步目录、设置、任务和业务记录 | 包含 | 保存好 ZIP，里面含有账号相关敏感数据 |
| QMediaSync API Key 的验证信息、TOTP 两步验证的加密数据 | 当前格式包含 | 另外保留原来的 `config/encryption.key`；API Key 明文仍需自行保存 |
| 浏览器登录状态 | 不包含 | 恢复后所有浏览器都要重新登录 |
| `config/config.yaml`、`config/.env`、`config/encryption.key`、证书和日志 | 不包含 | 另外备份整个 `config/` 目录 |
| 网盘文件、本地视频、STRM、字幕、海报和 NFO 文件 | 不包含 | 使用对应存储的备份方式，另外保留这些文件 |
| 外部 PostgreSQL 的数据目录 | 不包含原始数据目录，但 ZIP 包含 QMediaSync 的数据库内容 | 如需数据库原生备份或整机回退，另用 PostgreSQL 的备份方式保存 |

`config/encryption.key` 用来保护两步验证等本机敏感数据。只保留数据库 ZIP，无法补回丢失的原密钥。迁移时应在目标 QMediaSync 启动前放好原密钥；程序已启动时，替换文件后还要重启才会生效。

备份生成过程中不会暂停同步、上传或下载，保存的是同一时刻的数据库内容，不会把网盘和本地文件一起固定在那个时刻。需要整套环境可回退时，应先安排好正在运行的任务，再分别保存数据库、配置和文件。

## 手动备份

1. 打开「备份管理 → 备份记录」，点击「手动备份」。
2. 等待任务明确显示完成，再核对备份记录的时间和状态。进度达到 100% 或停止变化，都不能单独当作备份成功。
3. 在这条完成记录上点击「下载」，保存得到的 `.zip` 文件。
4. 把 ZIP 复制到其他磁盘、电脑或备份存储，不要把唯一副本留在运行 QMediaSync 的磁盘上。
5. 在合适的停机时间停止 QMediaSync，复制整个 `config/` 目录，完成后再启动。SQLite 用户尤其不要在程序仍写入时只复制一个 `.db` 文件；停机后保留整个目录更容易避免遗漏日志文件。

程序生成的 ZIP 保存在 `config/backups/`。Docker 部署对应挂载到容器 `/app/config` 的宿主机目录；Windows 和 Linux 发布版通常是程序旁的 `config/`。

下载后可用压缩软件检查 ZIP 能否正常打开，但“能解压”只说明压缩文件可读，不能代替恢复演练。重要数据建议在独立测试环境中恢复一次，并核对账号、同步目录、设置和记录。

## 自动备份

打开「备份管理 → 备份设置」：

1. 开启「启用自动备份」。
2. 设置「定时策略」，核对页面列出的「下 5 次执行时间」。默认策略为每天 `03:00`。
3. 设置「保留天数」和「最大备份数」，默认分别为 `7` 天和 `10` 个。
4. 点击「保存配置」。保存成功后立即按新策略安排任务，无需重启。
5. 到下一个执行时间后，在「备份记录」检查是否出现已完成的自动备份。

自动备份默认关闭。关闭开关会取消后续计划，已经开始的备份仍会继续。

保留天数和数量会同时生效：超过任意一项限制的历史完成备份，都可能在下一次新备份成功后被删除。**手动备份也在这套清理范围内**，需要长期保留的 ZIP 应及时下载到独立存储。

## 恢复前的准备

恢复会整体替换目标数据库，目标中后来新增的账号、设置和记录不会与备份合并。

- 先备份目标当前的数据和配置，确认可以回退。
- 确认来源和目标版本兼容。使用同一版本生成和恢复备份最容易核对；当前格式也要求数据库结构版本一致，不能把任意旧版本的 ZIP 当作通用迁移包。
- 提前安排同步、上传、下载和外部文件操作的暂停时间。保留正在操作的这个 QMediaSync 实例运行，以便从网页发起恢复；停止所有连接同一数据库的其他 QMediaSync 实例和外部写入程序。
- 换机器时，先准备好本地目录和 Docker 挂载，让恢复后的路径能找到正确文件。恢复后重启会重新加载定时任务和持久任务。
- 使用原来的 `config/encryption.key`。备份包含两步验证加密数据时，密钥不匹配会在修改数据库前被拒绝。

恢复只接受 `.zip`，文件大小上限为 1 GiB（页面显示为「1 GB」）。不要通过改扩展名、拆包或手动修改包内数据绕过校验。

## 从备份记录或本地 ZIP 恢复

两种入口任选其一：

- ZIP 仍在当前实例中：打开「备份管理 → 备份记录」，找到对应的完成记录，点击「恢复」。
- ZIP 保存在自己的电脑上：打开「备份管理 → 备份恢复」，拖入文件或点击「点击选择文件」，核对文件名后点击「开始恢复」。

接下来：

1. 阅读覆盖数据库和停机提示，确认目标正确后点击「确认恢复」。
2. 保持当前页面打开，等待明确的恢复结果。不要因页面暂时没有变化就重复提交，也不要在恢复期间手动重启。
3. 记录页面显示的成功或失败结果。恢复进入维护阶段后，其他业务功能会暂停。
4. 结果提示需要重启时，点击「重启服务」。页面没有这个按钮、提示不支持，或重启失败时，使用原来的部署管理方式重启 QMediaSync。
5. 等服务重新上线，按恢复结果登录：确认恢复已提交时，使用**备份中的管理员账号和密码**；最初校验就失败或已明确回滚时，仍使用**目标恢复前的账号和密码**。结果不确定时先核验数据库。恢复成功且原密钥已正确保留时，备份中管理员的原两步验证器可以继续使用。
6. 核对网盘账号、同步目录、本地路径、关键设置和业务记录，再检查任务是否按预期运行。

Docker Compose 可在原 Compose 文件目录执行 `docker compose restart qmediasync`，其中 `qmediasync` 要替换为实际服务名；Linux systemd 使用 `sudo systemctl restart qmediasync`；Windows 退出程序后重新打开。

**进入维护阶段后，无论恢复成功还是失败，都需要重启才能恢复业务。** 如果文件在最初校验时就被拒绝，尚未进入维护，则通常不需要重启。服务重新上线只表示程序启动了，仍需核对刚才的恢复结果和实际数据。

## 在 SQLite 和 PostgreSQL 之间迁移

当前备份格式支持 SQLite 与 PostgreSQL 双向恢复。**只改 `db.engine` 或数据库连接信息不会搬运数据**，它只会让程序连接另一份数据库。

按下面的顺序操作：

1. 在来源实例完成最终的手动备份并下载 ZIP，停止来源 QMediaSync，保存整个 `config/` 目录。迁移核对结束前保留来源数据和原版本程序。
2. 准备独立的目标配置目录和空数据库。选择 PostgreSQL 时先部署 PostgreSQL；选择 SQLite 时使用新的数据库文件。安装方式见 [数据库的选择](数据库的选择.md) 和对应平台的安装页。
3. 把原 `config/` 复制到目标位置，保留原 `encryption.key`。**在启动目标前**，按 [配置文件](配置文件.md) 修改目标副本中的数据库配置，让它明确指向新数据库，避免误连原库。目标使用 SQLite 时，给 `db.sqliteFile` 填一个尚不存在的新文件名，例如 `qmediasync-restored.db`，不要复用复制过来的旧数据库文件；同时调整目标机器的端口、目录挂载和文件权限。
4. 用与备份兼容的 QMediaSync 版本启动目标。空数据库需要按初始化页面创建临时管理员，初始化码在目标的启动日志中。
5. 登录目标，按照本页的「从备份记录或本地 ZIP 恢复」上传 ZIP、恢复并重启。恢复成功会替换临时管理员，之后用备份中的管理员登录；已明确回滚或最初校验失败时，仍使用临时管理员。
6. 逐项核对账号授权、同步目录、本地路径、媒体服务器连接、设置和记录。确认完成前不要让来源和目标同时处理同一批文件。

如果原来使用内嵌 PostgreSQL，先读 [更新与旧版迁移](更新与旧版迁移.md)。旧版迁移向导生成的 `migrate.zip` 不能直接当作当前的普通备份上传。

## 常见失败怎样处理

| 提示或现象 | 处理方式 |
| --- | --- |
| 备份任务失败，没有新的完成记录 | 检查磁盘剩余空间、配置目录权限和服务日志；保留已有备份，排除原因后重试 |
| 文件过大或上传返回 `413` | 先检查是否超过 1 GiB；未超过时再检查反向代理的上传限制，见 [反向代理配置](反向代理配置.md) |
| 归档损坏、内容缺失或校验失败 | 重新下载原始 ZIP，使用完整文件；不要手动补表、改清单或重新压缩来伪装成功 |
| 版本不兼容 | 在能读取原数据库的版本中完成升级并重新备份；保留原库，不直接修改 ZIP 中的版本号 |
| 两步验证密钥不匹配 | 停止目标 QMediaSync，放回来源 `config/encryption.key`，启动后重新发起恢复；丢失原密钥不能靠数据库 ZIP 补回 |
| 显示已回滚 | 本轮数据库修改已撤销；若已进入维护，仍需重启，再查日志排除原因 |
| 显示数据库已提交，但后续处理失败 | 数据可能已恢复，先保留结果和日志，按提示重启并核对，不直接重复覆盖 |
| 提交或回滚结果不确定 | 保留日志和现有数据，先核验数据库；不要把“任务失败”理解为“数据一定没变” |
| 重启后无法登录 | 确认恢复已提交时使用备份中的账号；最初校验失败或已回滚时使用目标原账号。核对密码和两步验证，仍无法登录时参照 [管理员与密码恢复](管理员与密码恢复.md) |

## 数据库修复与恢复有什么区别

「备份管理 → 数据库修复」中的「修复数据库」用于补齐缺失的表结构、字段、索引，并检查 PostgreSQL 主键序列。比如日志出现缺表或主键重复错误，可以先备份，再尝试修复并观察错误是否消失。

修复不会把已删除的业务记录找回来，也不能修复损坏的数据库文件。它还可能取消相互冲突的重复活跃传输任务；不要把它当作只检查、不修改的按钮。若提示数据库版本信息异常，先核对日志和备份，不能靠反复点击修复来重建丢失的数据。
