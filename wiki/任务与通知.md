# 任务与通知

同步、刮削、上传和下载是不同的工作，各有自己的记录。看到某一步完成后，下一步仍可能在排队；先找到对应页面，再根据状态处理问题。

## 到哪里看进度

| 想看什么 | 页面 | 重点检查 |
| --- | --- | --- |
| 整个目录生成 STRM 的结果 | STRM 同步 → STRM 同步记录 | 本次处理结果、失败范围、日志、后台保存和 Emby 刷新状态 |
| 识别、刮削和整理结果 | 刮削 & 整理 → 刮削记录 | 是否识别正确，刮削失败还是整理失败 |
| 元数据下载、本地复制、Emby 媒体信息提取 | 上传下载 → 下载队列 | 等待、进行中、完成或失败，展开查看路径和错误 |
| 元数据上传、刮削上传、目录监控上传 | 上传下载 → 上传队列 | 上传进度、完成处理、实际上传结果和源文件清理状态 |

下载队列的来源会显示「STRM 同步」「本地文件」或「Emby 媒体信息提取」；上传队列的来源会显示「STRM 同步」「刮削整理」或「目录监控上传」。排查时先确认任务来源，避免去错误的设置页修改配置。

## 同步记录的状态

点击一条同步记录进入详情，可以查看成功、失败、跳过数量，失败文件或目录，以及缺项清理、媒体库刷新、文件记录更新和日志。

| 状态 | 含义与下一步 |
| --- | --- |
| 待开始、运行中 | 任务尚未结束，继续观察进度和日志 |
| 已完成 | 本次同步生成阶段完成；元数据上传下载、后台保存或 Emby 刷新仍需看各自状态 |
| 部分完成 | 一部分文件已成功，另有文件失败。先看失败范围和原因，不必把成功部分也当成失败 |
| 扫描不完整 | 某些目录或列表未能可靠读完，程序会保护受影响范围，避免把“没读到”当成“已删除”。修正权限、授权或网络问题后再同步 |
| 失败 | 查看失败原因和日志，修正后重新启动同步 |
| 已取消 | 本次同步已停止；此前成功生成的文件可能仍然保留 |

旧记录没有处理明细时会显示「未记录」，这不等于成功、失败、跳过数量都是 0。

目录卡片上的「停止」用于取消等待中或正在运行的同步。页面提示已请求停止后，还要等待记录进入最终状态。相同来源的任务可能排队，程序重启后尚未开始的同步等待项需要重新触发。

## 上传队列为什么还有“完成处理”

上传不仅是把文件传到网盘，还要保存远端文件信息，并安排对应的 STRM 后处理。

- **等待上传、正在上传**：文件尚未完成传输。
- **等待完成处理、正在完成处理**：远端传输已经完成，正在等待或执行本地收尾。此时出现的收尾重试通常不需要重新上传整份文件。
- **上传完成**：上传任务已完成；目录监控产生的 STRM 生成或元数据复制仍可能继续。
- **上传失败、已取消**：展开任务详情查看原因，再决定是否重试。

任务详情中的“秒传”“恢复上传”“远端已存在”表示不同结果。远端已经有相同内容时可以跳过真实上传，不能把它当成发生了断点续传。

[目录监控上传](目录监控上传.md) 开启源文件清理后，详情还会显示清理状态和原因。上传完成但本地文件仍在，可能是 STRM 尚未处理完、后处理失败，或源文件已经变化。不要只看“上传完成”就手动删除尚未核对的源文件。

这类文件级 STRM 后处理不会出现在完整同步记录中，也没有单独的“STRM 生成队列”菜单。

## 暂停、重试和清空有什么区别

上传、下载队列都有状态筛选、刷新和批量操作：

| 操作 | 后果 |
| --- | --- |
| 全部暂停 | 暂停队列继续领取任务。上传队列中已经开始的传输会继续收尾，不会全部立即中断 |
| 全部恢复 | 继续处理队列中的等待任务 |
| 重试失败 | 重新安排失败任务；先修正授权、网络、权限或空间问题，避免再次失败 |
| 清空等待 | 删除等待任务记录，这批待传工作不会靠“全部恢复”继续执行 |
| 清空完成/失败 | 删除完成和失败的记录，不会撤回已经上传或下载的文件 |

清空等待不是暂停。尤其是同步产生的元数据任务，清空后可能造成字幕、NFO 或图片缺失，需要重新同步或扫描才能补齐；确实只是想暂缓处理，应使用暂停。

完整 STRM 同步执行时，程序也可能暂时暂停上传、下载队列，随后恢复，以协调两端文件处理。先看是否仍有同步正在进行，再判断队列是否异常。

记录会定期清理：同步历史每日清理创建时间超过 7 天的旧记录及日志；上传、下载队列也会清理超过 7 天的旧任务，其中可能包含积压的等待任务。发现失败或长期排队时及时处理，记录页面不适合长期存档。

## 配置通知渠道

这里的通知是 **QMediaSync 向你发送消息**，入口在「系统设置 → 通知管理」。Emby 向 QMediaSync 发送媒体和播放事件的配置见 [Emby 通知配置](Emby-通知配置.md)。

1. 进入「通知管理」，点击「添加渠道」。
2. 选择通知类型，填写渠道名称和对应凭据。
3. 点击「创建」，再点击该渠道卡片的「测试」。测试会向真实接收端发送一条消息，请确认已经收到。
4. 点击「规则」，保留需要接收的事件，关闭不需要的事件。
5. 确认渠道卡片总开关已开启。渠道和规则保存后生效，不需要重启 QMediaSync。

| 渠道 | 需要填写 |
| --- | --- |
| Telegram | 机器人的 Bot Token 和接收会话的 Chat ID；先让机器人能够向目标会话发消息 |
| MeoW | 接收昵称，可按所用服务填写 API 地址 |
| Bark | 设备密钥；自建服务时填写服务器地址，也可设置声音和图标 |
| Server酱 | 页面中的 `SCKEY` 和对应 API 地址；所用服务需要支持 `<API 地址>/<SCKEY>.send` 这一接口形式 |
| 自定义 Webhook | 接收服务的请求地址、请求方法、消息模板，以及服务要求的鉴权和请求头 |

新建渠道默认启用，事件规则也默认启用。可以给不同接收人建立多个同类型渠道，并分别选择规则。

## 选择通知事件

目前规则包括：

- STRM 同步完成、STRM 同步错误。
- 刮削完成、刮削错误。
- 系统警告。
- Emby 媒体添加、Emby 媒体移除。
- Emby 播放开始、Emby 播放暂停、Emby 播放停止。

日常事件通知需要**渠道总开关和对应事件规则同时开启**。播放事件比较频繁，不需要时可关闭；Emby 相关事件还依赖 [Emby 通知配置](Emby-通知配置.md) 中的事件接收配置。

「测试」直接发送测试消息，不按事件规则筛选。因此测试成功只能证明本次渠道能发送消息，不能证明 Emby 事件已经接通，也不能证明所有规则都已启用。

## 自定义 Webhook 怎么填

请求方法支持 `GET` 和 `POST`；`POST` 可选择 JSON、Form 或 Text。按接收服务的接口要求选择数据格式和鉴权方式，不能只填一个地址就假定所有服务都使用相同参数。

消息模板支持以下变量：

| 变量 | 内容 |
| --- | --- |
| `{{title}}` | 通知标题 |
| `{{content}}` | 通知正文 |
| `{{timestamp}}` | 格式为 `YYYY-MM-DD HH:mm:ss` 的时间文字，不是 Unix 秒数 |
| `{{image}}` | 图片 URL，没有图片时为空 |

简单的 Text 消息可以写成：

```text
【{{title}}】
{{content}}
{{timestamp}}
```

使用 `GET` 时，渲染后的模板放入一个查询参数，参数名默认是 `q`；请求地址填接收服务地址，不要把消息模板当作完整 URL。需要 Token 或自定义请求头时，使用页面对应的鉴权和请求头设置。

## 测试能收到，日常消息却收不到

先检查渠道总开关和对应规则，再确认事件实际发生。Emby 事件需要另外检查 Emby 是否把事件送到了 QMediaSync；同步、刮削通知则应核对对应任务的结果和日志。

如果连测试都失败，先检查 QMediaSync 所在机器的网络、接收地址、密钥和接收人信息。不要通过反复创建相同渠道来代替修正原渠道配置。
